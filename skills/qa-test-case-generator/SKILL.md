## 0. TC 생성 Phase 워크플로우 (Approval Protocol)

**상세 Phase 정의(Phase 0~8)와 각 단계별 승인 규칙은 AGENTS.md 13항을 그대로 따릅니다.** 요약:

- Phase 0(사전 질의: 프로젝트/URL/단위·통합/코드·정책기반) → Phase 1(분석) → Phase 2(범위 산정) → Phase 3(TC 산출) → Phase 4(TC 작성/HTML 생성)까지 **각 단계마다 개별 승인**을 받습니다.
- Phase 4가 승인돼도 자동화 테스트 실행(Phase 5)은 **별도 요청이 있어야만** 시작합니다.
- Phase 3에서 확정된 범위(TC 건수/모듈)를 Phase 4에서 임의 확장하지 않습니다. 확장 필요 시 Phase 3을 재제출해 다시 승인받습니다.
- 150건 이상 대규모 TC는 50~65건 단위 배치로 나누어 순차 전달합니다.

## 1. 근거 확보 절차 ★ (기준문서 없는 실서비스 대상 필수)

기준문서가 없는 경우, 추측으로 넘어가지 않고 아래 순서로 **실제 근거를 최대한 확보**합니다:

```
1순위. 대상 URL/파일을 직접 접근·분석
2순위. 하위 경로 다각도 시도 (상품상세/장바구니/정책페이지 등)
3순위. 검색으로 화면 스니펫/캡처 정보를 보조 근거로 수집
         (단, 이것만으로는 확인 필요 표시 유지)
4순위. 사용자에게 스크린샷 업로드 명시적 요청
         → 업로드된 이미지는 반드시 실제 내용 확인 후 근거로 사용
```

- 접근 성공/실패 여부와 관계없이 **시도 결과를 사용자에게 투명하게 보고**합니다
- 동일 정보에 대해 **페이지마다 다른 값** 발견 시(예: 무료배송 기준이 배너와 메타태그에서 다름) → 숨기지 않고 **데이터 정합성 TC(12. 데이터 정합성 검증)로 등록**합니다

## 3. TC 컬럼 스키마 (가변)

TC 컬럼은 프로젝트 요건에 따라 **유연하게 조정 가능**합니다. 기본 구성은 아래를 따릅니다.

| No | 컬럼 | 작성 규칙 |
|----|------|----------|
| 1 | **TC ID** | `TC_{모듈코드}_{3자리숫자}` (예: TC_PD_001) |
| 2 | **대분류** | 상품/구매프로세스/클레임/회원/전시/고객센터/품질·비기능/예외·회귀 등 |
| 3 | **중분류** | 모듈명 (예: 상품상세, 장바구니, 주문결제) |
| 4 | **소분류** | 세부 기능명 (예: 옵션선택, 수량정책, 귀책구분) |
| 5 | **플랫폼** | `Web` / `App` / `Web+App` / `API` / `Admin` |
| 6 | **유형** | `UI` / `기능` / `API` / `데이터` / `성능` / `보안` / `회귀` / `Boundary` / `크로스브라우저` / `접근성` |
| 7 | **테스트 항목(시나리오)** | "무엇을 검증하는가"를 명사형으로 — 보통 "~검증"으로 끝맺음. 불확실 시 `[확인필요]` 접두 |
| 8 | **기준문서** | `{파일명}_{버전}_{페이지}` 형식. 없으면 `-` |
| 9 | **우선순위** | P1 / P2 / P3 |
| 10 | **사전조건** | 절차 수행 전 미리 세팅된 환경·계정·데이터 상태값만 (동작 동사 금지) |
| 11 | **테스트 수행 절차** | 테스터가 실제 수행하는 액션, 번호 나열. 결과 서술 금지 |
| 12 | **기대결과** | 절차 번호와 1:1 대응하는 시스템 반응. 절차 재진술 금지 |
| 13 | **테스트 데이터** | 수행에 필요한 구체적 입력값, 계정, API 파라미터, 샘플 데이터 |
| 14 | **실행결과** | Pass / Fail / Blocked / N/A (HTML 드롭다운, 기본값 미입력) |
| 15 | **담당자** | 자유 입력 (기본값 미입력) |
| 16 | **이슈내용 요약** | 자유 입력 (기본값 미입력) |
| 17 | **이슈링크** | Jira 등 버그트래커 링크 (기본값 미입력) |

> 컬럼 추가/제거/순서 변경은 프로젝트 요건에 따라 허용됩니다.

## 4. 컬럼 간 역할 분리 ★★★ (중복 서술 금지)

동일 문장이 테스트항목→사전조건→절차→기대결과에서 형태만 바뀌어 반복되는 것은 **저품질 TC**의 대표 패턴입니다.

| 컬럼 | 담아야 할 정보 | 담으면 안 되는 정보 |
|------|--------------|------------------|
| 테스트 항목 | 검증 구분값 (명사형, "~검증"으로 끝) | 구체적 액션, 결과 문구, 절차 나열 |
| 사전조건 | 절차 전 세팅된 환경·데이터 상태값 | 동작 동사 (~클릭, ~진입 등) |
| 테스트 수행 절차 | 테스터가 실제 수행하는 액션 (번호 나열) | 결과 서술 (~노출된다, ~반영된다) |
| 기대결과 | 절차 번호에 1:1 대응하는 시스템 반응 | 절차/항목 문장 재진술 |
| 테스트 데이터 | 입력값/계정/API 파라미터/샘플 데이터 | 기대결과 서술 |

**작성 권장 순서**: ① 사전조건(세팅값) → ② 절차(액션만) → ③ 기대결과(번호별 반응) → ④ 테스트 항목(①~③ 압축) → ⑤ 테스트 데이터(사용된 값 정리)

**Before/After 예시**
```
[중복 발생 예 - 지양]
테스트항목: 옵션 선택 시 가격/이미지 갱신
절차     : 1) PDP 진입 2) 옵션 선택 동작 수행
기대결과 : 옵션 선택 시 가격/이미지 갱신이 확인된다  ← 테스트항목 재진술, 정보 추가 없음

[역할 분리 예 - 지향]
테스트항목: 옵션 선택 시 가격·대표이미지 실시간 반영 검증
사전조건 : 옵션별 상이한 가격/이미지가 설정된 상품 (상품코드: PRD-20190001)
절차     : 1) PDP 진입 2) [색상] 드롭다운에서 "블랙" 선택
기대결과 : 1) 즉시 "블랙" 옵션 가격으로 갱신됨 2) 대표 이미지가 블랙 옵션 이미지로 전환됨
테스트 데이터: 상품코드=PRD-20190001, 선택옵션=블랙, 예상가격=29,900원
```

## 6. 우선순위 판단 기준

### P1 (Critical) — 즉시 차단
- 결제/환불/재고에 영향을 주는 모든 케이스
- 데이터 정합성 검증 (가격, 수량, 금액 계산식)
- 로그인/인증 관련 보안 케이스
- 핵심 구매 플로우 (상품 선택 → 장바구니 → 결제 → 완료)
- 과판매, 이중 결제 등 비즈니스 리스크 즉시 발생

### P2 (Major) — 주요 기능
- 프로모션/쿠폰/포인트 적용 로직
- 취소/반품/교환 플로우
- 크로스 플랫폼 동기화
- 배송 정책 (조건부 무료배송, 도서산간 등)
- Empty State, 오류 메시지 UI

### P3 (Minor/예외/회귀)
- UI 시각 요소 (색상, 레이아웃, 애니메이션)
- 최대값 제한, 예외 케이스
- 마이페이지 조회성 기능
- `[확인필요]` 태그가 붙은 모든 케이스 (정책 확정 후 상향 조정)

> P1이 전체 TC의 50%를 초과하면 남용으로 판단하고 재조정합니다.

## 7. 사전조건 작성 규칙

- **원칙**: 기대결과를 얻기 위해 절차 수행에 **실제로 필요한 항목만** 남깁니다
- 계정 정보가 결과에 영향을 주지 않는 케이스 (데이터 정합성, 검색/리스트, 성능, 크로스브라우저 등)는 → **`특이 사전조건 없음`** 한 줄로 표기
- 계정 포함이 필요한 모듈: 로그인/마이페이지/주문결제/취소반품/프로모션/멤버십
- 계정 세분화 형식:
  ```
  1) Acc_Normal (기본 통합회원)
  2) 결제수단 : 등록카드 1개 - 신한카드
  3) 보조결제수단 : 포인트 5,000P 보유
  4) 쿠폰 : 10% 할인쿠폰 1매 보유
  5) 배송지 : 기본배송지 서울 강남구 등록
  ```
- 값이 "0개/0P/없음" 등 기본값이고 해당 시나리오와 무관하면 해당 줄 생략
- 검증도구(개발자도구/프록시) 안내는 사전조건이 아닌 **절차(수행 단계)로 이동**
- **글로벌/역직구 서비스**: 계정 매트릭스에 배송국가/차단지역 축을 반드시 포함합니다
  ```
  - Acc_Guest (배송국가: US)
  - Acc_Guest (배송국가: 차단지역 — 배송 불가 국가 대표값)
  - Acc_Member_ShipCountry (국내 회원, 해외 배송지 등록)
  ```
- 표준 계정 목록: **AGENTS.md 12항** 참조

## 9. 기대결과 작성 표준

- **절차 번호와 1:1 대응**: 절차 3번 액션의 결과는 기대결과 3번에 기술
- **검증 가능한 구체적 값/상태**: 필드명·예상값·상태값을 구체적으로 기술
- **모호한 표현 금지**: "정상 동작한다" 단독 사용 금지
- **CSS 수치 표기**: 근거(Figma/캡처화면) 있을 때만 `*` 보조설명으로 분리
  ```
  구매 버튼이 Disabled 상태로 노출, 클릭 시 "옵션을 선택해주세요" 문구 노출
  * 비활성화 버튼 배경색 : Hex #D1D5DB (근거: Figma frame #47:894)
  ```
- **정책 미확정**: `* [확인필요] {확인 내용}` 형식으로 기대결과 하단에 표기
- **API 응답**: HTTP Status Code + 핵심 Response 필드명·예상값 명시

**좋은 API TC 기대결과 예시**
```
기대결과:
1~3. Request body 확인:
     - orderQty: "1" (문자열)
     - paymentMethod: "CARD"
     - couponId: "CP20190001"
     응답 HTTP Status: 200 OK
     응답 body: { "orderId": "{신규 주문번호}", "status": "PAYMENT_COMPLETE" }
```

## 11. TC 확장 기법 ★ (대규모 커버리지 확보)

<!-- [수정 전 2026-08-18] 목표 건수(150~200건+)를 채울 때, 근거 없는 화면을 상상해서 늘리지 않습니다. -->

**정해진 목표 건수를 채우기 위해서가 아니라, 도출 가능한 최대치를 뽑아내기 위해** 아래 5가지 기법을 적용합니다. **근거 없는 화면을 상상해서 늘리지 않습니다** — 늘어난 개수는 항상 실제 근거(정책서/화면/기존 TC 패턴)에서 나와야 합니다.
이미 확보한 근거를 아래 5가지 기법으로 체계적으로 전개합니다:

| 기법 | 설명 | 적용 예 |
|------|------|---------|
| **상태값 전개** | UI 요소가 가질 수 있는 실제 상태값들을 각각 TC로 분리 | 배송 상태: 결제완료/배송중/배송완료/취소/반품 |
| **경계값(Boundary)** | 실제 최소/최대값, 0/1 등 경계 조건 | 수량 1 미만 차단, 최대 99개 초과 |
| **조합(Combination)** | 필터/옵션 UI들을 2~3개씩 동시 적용 | 카테고리+브랜드+가격 필터 동시 적용 |
| **예외(Exception)** | 정책 문구 기반의 실패/제한 케이스 | 쿠폰 최소금액 미충족, 결제 거절 |
| **회귀(Regression)** | 한 화면 설정 변경이 다른 화면에 미치는 교차 영향 | 배송지 변경 → 장바구니 배송비/가능여부 재검증 |
