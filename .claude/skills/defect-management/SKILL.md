# 결함(Defect) 관리

자동화 테스트(`playwright-automation` 스킬)가 실패를 발견하면, 그 실패를 응답 텍스트로 한 번 보고하고 끝내지 않고 **`project\{프로젝트명}\TC\defects.json`에 결함 레코드로 영속화**합니다. Jira 등 외부 이슈트래커 없이 이 저장소 안에서 자체적으로 관리합니다.

### 20-1. 파일/폴더 컨벤션

- **레코드 파일**: `project\{프로젝트명}\TC\defects.json` (배열, Git 관리 대상)
- **스크린샷**: `project\{프로젝트명}\TC\defects\{결함ID}.png` — 실패 시점의 스크린샷을 `_scratch`/`test-results`(Git 비대상, 휘발성)에서 이 경로로 **복사**해 영구 보관합니다 (원본 경로만 참조하면 리포트 삭제 시 증거가 사라지므로 반드시 복사).
- **콘솔로그**: `project\{프로젝트명}\TC\defects\{결함ID}.console.json` — **404/500 등 네트워크 에러나 JS 예외로 이슈를 발견해 스크린샷을 캡처하는 모든 경우, 스크린샷과 동시에 그 시점의 콘솔/네트워크 로그도 함께 캡처해 영구 보관**합니다(2026-08-24 확정). 형식은 `{ "consoleErrors": [...], "failedRequests": [...] }`. 경로별 확보 방법:
  - **자동화(Phase 5) 경로**: `_shared/testFixtures.js`가 실패 시 이미 `testInfo.attach('console-network-errors', {...})`로 같은 형식의 JSON을 첨부해두므로, 결함 레코드 생성 시 스크린샷과 함께 이 첨부파일도 위 경로로 복사합니다.
  - **수동 재현/Phase 1 관찰 경로**: 스크린샷을 찍기 전에 `page.on('console', ...)`/`page.on('pageerror', ...)`/`page.on('response', ...)` 리스너를 먼저 등록해 같은 형식(`consoleErrors`/`failedRequests`)으로 수집한 뒤, 스크린샷과 같은 타이밍에 저장합니다 — 스크린샷만 찍고 콘솔로그 캡처를 생략하지 않습니다.
- **결함 ID 형식**: `DEF_{프로젝트명}_{3자리 순번}` (예: `DEF_ABC마트_001`)

### 20-2. 레코드 스키마

```json
{
  "defectId": "DEF_ABC마트_001",
  "tcId": "TC_CRT_012",
  "module": "장바구니",
  "screenName": "장바구니 메인",
  "severity": "P1",
  "status": "신규",
  "summary": "콘솔 에러 감지: 장바구니 담기 클릭 시 TypeError 발생",
  "testEnv": "Chromium (Playwright), http://192.168.10.116:30180",
  "testSteps": "1) 장바구니에 상품 1건 담기 2) 수량 변경 3) 담기 버튼 재클릭",
  "actualResult": "담기 버튼 재클릭 시 콘솔에 TypeError 발생, 수량이 반영되지 않음",
  "expectedResult": "수량 변경 후 재클릭 시 에러 없이 수량이 갱신되어야 함",
  "detectedAt": "2026-08-14",
  "source": "automation",
  "screenshot": "TC/defects/DEF_ABC마트_001.png",
  "consoleLog": "TC/defects/DEF_ABC마트_001.console.json",
  "assignee": "",
  "issueLink": "",
  "history": [
    { "at": "2026-08-14", "status": "신규", "note": "Playwright 자동 실행 중 최초 발견" }
  ]
}
```

- `summary`: **`{결함 발생 화면명} > {실제결과 요약}` 형식**으로 짧게 기입합니다(2026-08-21 확정, 20-6항 뷰어 표기 규칙과 동일). 구체적 기술 세부사항은 `summary`에 넣지 않고 `actualResult`에 담습니다.
- **`module`과 `screenName`은 서로 다른 개념이며 한 값에 섞어 쓰지 않습니다** (2026-08-26 확정, 공통 정책 — 향후 모든 프로젝트 동일 적용). `module`은 AGENTS.md 2항 `대분류`(SKILL.md 5항 모듈 코드 매핑 표의 값, 예: "전시")만 담고, 그 결함이 발생한 구체적 화면(예: "MD's PICK")은 `screenName`에 별도로 기재합니다. `module`에 "전시(MD's PICK)"처럼 화면명을 괄호 병기하지 않습니다 — 대시보드 등에서 모듈 단위로 집계할 때 같은 모듈의 화면마다 별도 항목으로 쪼개져 집계가 깨지기 때문입니다. 여러 화면에 걸친 결함이라 화면명을 하나로 특정할 수 없으면 `screenName`은 빈 값으로 두고(강제로 하나 고르지 않음), `module`도 실제 대분류에 해당하지 않으면("공통" 등 범용 분류가 더 적절하면) 무리해서 특정 대분류에 끼워 맞추지 않습니다.
- `severity`: 해당 TC의 우선순위(P1/P2/P3)를 그대로 상속합니다.
- `testEnv`(선택)/`testSteps`(필수)/`actualResult`(필수)/`expectedResult`(필수): 해당 TC의 사전조건·수행절차·기대결과(AGENTS.md 2항 표준 필드)와 실제 관찰된 결과를 결함 레코드에도 함께 남겨, TC 문서를 별도로 대조하지 않아도 결함 하나만 보고 재현/판단할 수 있게 합니다. `testEnv`는 특이사항이 없으면 생략 가능하지만 나머지 3개는 항상 채웁니다.
- `status` 허용값: `신규` / `처리중` / `재검증대기` / `완료` / `보류` / `재발생`
- `source`: `automation`(자동화 테스트 발견) / `manual`(수동 QA 실행 중 발견, 사용자가 채팅으로 직접 등록 요청한 경우) / `observation`(Phase 1 관찰 스크립트 등 비-자동화 탐색 중 어시스턴트가 발견, 2026-08-20 추가)
- **스크린샷·콘솔로그 확보 원칙**: `source`가 `observation`이어서 아직 실패 스크린샷/콘솔로그가 없는 결함을 발견하면, 해당 결함을 확인하는 자동화 테스트를 실행하거나(`playwright-automation` 스킬 방식으로 `--grep`) 임시 스크립트로 재현해 스크린샷과 콘솔로그를 **동시에** 확보한 뒤 20-1항 경로에 저장합니다(스크린샷만 확보하고 콘솔로그를 누락하지 않음). 데모 환경은 계속 변화할 수 있으므로, 재검증 시 증상이 최초 발견과 다르면(예: 500→CORS 에러로 변경) 결함 레코드와 관련 TC를 현재 증상 기준으로 갱신하고 history에 재검증 시점을 기록합니다(임의로 과거 기록을 지우지 않음).

### 20-3. 자동 생성/갱신 규칙 (자동화 테스트 실행 시마다)

1. 실패한 TC마다 `defects.json`에서 **같은 `tcId`의 열려있는(상태가 `완료`가 아닌) 레코드**를 찾습니다.
   - 없으면: 새 레코드를 `신규` 상태로 생성하고 스크린샷과 콘솔로그를 함께 복사합니다(20-1항).
   - 있으면: 새 레코드를 만들지 않고 기존 레코드의 `history`에 "재실행에서도 동일하게 실패" 항목만 추가합니다 (중복 생성 금지).
   - 상태가 `완료`였던 레코드가 다시 실패하면: 상태를 `재발생`으로 되돌리고 `history`에 기록합니다.
2. 과거에 실패했던 TC가 이번엔 **통과**했는데 해당 TC에 열려있는 결함 레코드가 있다면, **자동으로 `완료` 처리하지 않습니다.** 대신 보고 시 "TC_XXX 재검증 통과 — 관련 결함 DEF_XXX를 완료 처리할까요?" 라고 물어보고, 사용자가 명시적으로 확인해준 뒤에만 상태를 `완료`로 변경합니다 (우연한 1회성 통과로 결함을 놓치지 않기 위함).

### 20-4. 대화를 통한 결함 관리

같은 프로젝트를 다루는 대화 세션 안에서 자연어로 요청하면 `defects.json`을 조회/수정합니다.

- `"결함 목록 보여줘"` / `"신규 상태인 결함만 보여줘"` → 조회 후 표로 정리해 응답
- `"DEF_ABC마트_001 담당자를 홍길동으로 지정해줘"` → 해당 레코드 `assignee` 수정
- `"DEF_ABC마트_001 처리중으로 변경해줘"` / `"...보류로 변경해줘"` → `status` 및 `history` 갱신
- `"DEF_ABC마트_001 완료 처리해줘"` → `status`를 `완료`로 변경 (20-3-2 확인 절차의 응답으로도 사용)
- 파일 수정 자체는 즉시 반영하되, **Git 커밋은 AGENTS.md 18항 규칙대로 사용자가 최종 승인한 시점에만** 수행합니다.

### 20-6. TC HTML 뷰어 "결함현황" 탭

Phase 4 HTML 뷰어(AGENTS.md 14항) 생성/재생성 시, TC 탭들과 별도로 **"🐞 결함현황" 탭**을 추가합니다.

- 뷰어를 생성할 당시 `project\{프로젝트명}\TC\defects.json`의 **전체 내용**을 읽어 두 번째 JS 배열(`defectData`)로 임베드합니다 (이번 배치 결함만이 아니라 프로젝트 누적 전체).
- **KPI 카드**: 전체 결함 / 신규 / 처리중 / 완료 (상태별 카운트)
- **상태별 필터 pill**: 전체 / 신규 / 처리중 / 재검증대기 / 완료 / 보류 / 재발생
- **테이블 컬럼 순서**: 결함ID, 모듈, 화면명, 심각도(P1/P2/P3 배지), 상태(드롭다운 — 실행결과 드롭다운과 동일한 이벤트 위임 패턴), 요약, 상세내용, 스크린샷(썸네일), 발견일, 관련 TC ID(클릭 시 해당 TC 목록 위치로 이동), 비고(자유입력 — 내부 필드명은 `issueLink` 그대로 유지, 화면 라벨만 "비고")
- **요약 컬럼 표기 형식** (2026-08-21 확정): `{결함 발생 화면명} > {실제결과 요약}` 형식으로 짧게 기입합니다 (예: `상품상세 > 비로그인 상태에서 위시리스트 버튼 클릭 시 로그인 페이지 자체에서 리소스 3건 404로 실패`). 구체적인 기술 세부사항(실패한 리소스 경로, href 값, 에러 다이제스트 등)은 요약에 넣지 않고 상세내용의 `[실제결과]`에 담습니다.
- **상세내용 컬럼** (2026-08-21 개선): 20-2항의 `testEnv`(있을 때만)/`testSteps`/`actualResult`/`expectedResult`를 한 셀에 줄바꿈으로 나열하지 않고, 항목별로 한눈에 구분되도록 `[환경]` / `[절차]` / `[실제결과]` / `[기대결과]` 라벨을 붙인 구획(`<div class="defect-section">`, 라벨은 작고 흐린 색+굵게, 본문은 줄바꿈 유지)으로 분리해 렌더링합니다.
- **스크린샷 컬럼**: 목록에 작은 썸네일(`<img src="defects/{결함ID}.png">`, 상대경로)을 바로 표시하고, 클릭 시 모달로 원본 크기를 확대해 보여줍니다 (HTML 뷰어 파일이 `TC\` 바로 아래 저장되므로 `defects\` 하위 참조로 항상 해석 가능).
- **담당자(assignee) 필드**: `defects.json` 스키마에는 유지하되(20-4항 자연어 배정 요청 등에서 계속 사용), 이 뷰어 테이블에는 컬럼으로 노출하지 않습니다.
- 나머지 스타일(GitHub Dark 테마, 반응형 등)은 AGENTS.md 14항 기존 규칙을 그대로 따릅니다.
- **URL 해시로 결함현황 탭 바로 열기**: 탭 전환 상태를 관리하는 변수(`currentTab` 등) 선언 직후, 스크립트 로드 시 `location.hash`(디코딩 후 `#` 제거)가 `"결함현황"`을 포함하면 그 변수를 결함현황 탭 값으로 초기화합니다. 이렇게 해야 외부에서 `{뷰어파일}.html#결함현황` 형태로 링크했을 때 첫 렌더링부터 결함현황 탭이 선택된 상태로 열립니다 (탭 목록의 pill을 클릭하는 기존 전환 로직과는 별개로, 초기 진입 시점에만 적용).

### 20-7. 기존 결함으로 재검증이 막힌 TC — N/T 처리 (2026-08-21 확정)

> 실행결과 값(Pass/Fail/N/A/N/T) 전체 정의는 AGENTS.md 10항 "실행결과 값 정의" 표를 참조하세요. 아래는 그중 N/T 사용 기준을 더 자세히 다룹니다.

같은(또는 상위) 결함이 이미 `신규`/`처리중` 등 미해결 상태로 등록되어 있어서, 그 결함 때문에 특정 TC가 정상적으로 Pass/Fail을 판정할 수 없는 경우(예: 로그인 플로우 자체의 알려진 리소스 404가 그 플로우를 거치는 모든 TC를 자동으로 실패 처리시키는 경우) 처리 방법입니다.

- **실행결과**: `Fail`이 아니라 **`N/T`**로 기록합니다 — 이 TC 자체의 기능이 깨졌다는 뜻이 아니라, 이미 알려진 다른 결함 때문에 깨끗한 판정이 불가능하다는 뜻입니다.
- **비고(remark)**: `"해당 결함에 따른 테스트 불가 (관련 결함: {결함ID})"` 형식으로 기재합니다. 관련 결함이 여러 개면 쉼표로 나열합니다.
- **관련 결함 판단 기준**: `defects.json`의 `tcId` 필드와 정확히 일치하는 TC뿐 아니라, **같은 근본 원인(예: 로그인 플로우 프리페치 404, 배너 href 프로토콜 누락)으로 인해 실패하는 다른 TC들도 모두 포함**합니다 — 결함 하나가 여러 TC에 파급되는 경우가 많으므로 tcId 1:1 매칭에 국한하지 않습니다.
- **결함 자체를 재현/확인하는 목적의 TC**(예: "OOO 접근 시 404 에러 검증"처럼 그 결함 발생을 검증 대상으로 삼는 TC)는 N/T가 아니라 **의도된 대로 Fail 유지**합니다 — 그 결함이 실제로 재현되는지 확인하는 것이 이 TC의 목적이므로, 결함이 해결되지 않은 한 계속 Fail로 남아 있는 것이 정상입니다.
- 해당 결함이 `완료` 처리되면, 관련된 N/T TC들도 함께 재실행하여 정상 Pass/Fail로 갱신합니다(기계적으로 자동 전환하지 않고 재실행 후 실제 결과로 반영).
