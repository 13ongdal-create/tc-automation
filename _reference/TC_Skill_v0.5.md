# 이커머스 QA TC 생성 스킬 v0.5

> v0.4 대비 변경: Phase 4 HTML 뷰어에 TC 데이터 JSON 저장/불러오기 기능을 표준 스펙으로 추가(§9). 상세 변경사항은 문서 최하단 §15 참조.

## 0. 기본 원칙 (Approval Protocol)

1. **[Phase 1: 도메인/근거 확보] → [Phase 2: 계정 매트릭스] → [Phase 3: 시나리오검토표+배분계획 제출] → [사용자 승인] → [Phase 3.5: TC 자체검증(기준문서 있는 경우만)] → [Phase 4: HTML 생성]** 순서를 반드시 지킨다.
2. Phase 3에서 사용자와 확정한 범위(TC 건수/모듈)를 Phase 4에서 **임의로 확장하지 않는다.** 확장이 필요하면 반드시 Phase 3을 다시 제출해 승인받는다.
3. 확인되지 않은 정책/동작은 절대 임의로 "정상 동작함"이라 단정하지 않는다.
4. **최초 스코프 협의 시점(Phase 3)에 대상 서비스 규모를 고려해 150~200건 이상의 목표 건수를 기본 옵션으로 함께 제시한다.** 사용자가 소규모를 원하면 축소하되, "일단 적게 만들고 나중에 늘리는" 방식보다 "처음부터 목표 규모를 정하고 시작"하는 편이 재작업을 줄인다.

## 1. 근거 확보 절차 (★ 신규 — 기준문서 없는 실서비스 대상 필수)

기준문서가 없는 경우, 추측으로 넘어가지 않고 아래 순서로 **실제 근거를 최대한 확보**한다.

```
1순위. 대상 URL을 web_fetch로 직접 접근 시도
2순위. robots.txt 등으로 차단되면, 관련 하위 경로(카테고리/상품상세/장바구니/이벤트/정책·법정고지 페이지 등)를 다각도로 시도
        - 상품상세: 검색으로 실제 상품 URL 패턴을 먼저 찾은 뒤 접근
        - 정책/법정고지 페이지(예: 특정상거래법 표시 등)는 결제·배송 정책의 공식 근거로 유용
3순위. 그래도 막히면 web_search로 해당 화면의 스니펫/캡처 정보를 보조 근거로 수집(단, 이것만으로는 "캡처된 화면" 근거로 인정하지 않고 이후에도 확인 필요 표시 유지)
4순위. 위 방법으로도 확보 불가한 화면은 사용자에게 스크린샷 업로드를 명시적으로 요청한다. 업로드된 이미지는 반드시 view 도구로 실제 내용을 확인한 뒤 근거로 사용한다(요청만 하고 확인을 생략하지 않는다).
```

- 접근 성공/실패 여부와 관계없이 **시도 자체와 결과를 사용자에게 투명하게 보고**한다(예: "robots.txt로 차단되어 접근 실패").
- 확보한 근거는 §2의 "허용된 근거" 목록에 "캡처된 화면(직접 fetch)" / "사용자 업로드 스크린샷" 형태로 구분해 기록한다.
- 근거 확보 과정에서 **동일 정보에 대해 서로 다른 값(예: 무료배송 기준 문구가 페이지마다 다름)**을 발견하면, 이를 숨기지 않고 별도 TC(§11 데이터 정합성 검증)로 등록한다 — 이는 놓치기 쉬운 실제 QA 발견사항이므로 적극적으로 표면화한다.

## 2. 기준문서 대조 절차 (★ 최우선 규칙)

| 상황 | 처리 |
|---|---|
| 기준문서(정책서/화면설계서/Figma/PRD/ERD) **없음** | §1 근거 확보 절차 수행 → 그래도 확보 안 되는 항목만 §5 예외 처리(확인필요 태그) 적용 |
| 기준문서 **있음** | HTML 생성 **전** 아래 우선순위로 대조 검토 후 생성 |

기준문서 대조 우선순위(항상 이 순서로 점검):
```
1순위. 문서가 최신 버전인지 확인
2순위. 문서 내 삭제/수정/추가 사항 파악 → TC에 반영
3순위. 문서의 기준 정보에 TC가 부합하는지 최종 점검
```
- CSS/화면 관련 기대결과는 Figma·화면설계서가 있는 경우 **최신 버전 여부를 선(先) 확인** 후 재검토한다.
- 문서만으로 판단이 애매한 사항은 **HTML 생성 전 반드시 사용자에게 질의**하고 답변을 받은 뒤 생성한다. (임의 추정 금지)

## 3. 근거 원칙 — 추측 금지 (No Speculation) ★★★ 핵심

모든 TC는 아래 근거 중 하나 이상을 명시할 수 있어야 한다.

**✅ 허용된 근거**
- Figma frame 또는 캡처된 화면(직접 fetch로 실제 확인된 UI)
- 사용자 업로드 스크린샷(view 도구로 실제 확인한 것)
- PRD/ERD 섹션(Notion 원문에 명시된 내용)
- Slack 스레드 결정 사항
- ERD의 API spec(엔드포인트 + 필드)
- 메뉴트리(V3) 항목
- 기존 Regression TC 패턴(재사용)
- 공식 정책/법정고지 페이지 원문
- `skillset` 도메인 지식(명시된 것만)

**❌ 금지된 근거(추측)**
- "일반적인 UX 패턴"
- "다른 서비스는 이렇게 함"
- "이럴 것으로 예상됨"
- "스펙에 명시되지 않았지만 필요할 것 같음"
- "typical form pattern"
- 사용자가 "확인 없이 그냥 작성해달라"고 요청하더라도, 근거 없는 세부 UI 요소(필드명/버튼라벨 등)를 새로 만들어내는 것은 하지 않는다. 대신 §1 근거 확보를 재시도하거나, 확보된 근거 범위 내에서만 우선순위를 재산정한다(무조건 P3로 낮추는 것이 아니라 "근거가 있는 만큼" 정상 우선순위를 부여).

**⚠️ 예외 처리**: 근거가 불확실하지만 QA 관점에서 반드시 검증이 필요한 경우
1. TC 제목(테스트 항목) 앞에 `[확인필요]` 태그 추가
2. 기대결과에 "스펙 확정 시 재검증 필요" 명시
3. 우선순위를 **P3**로 강제 지정(스펙 확정 후 상향 조정)

## 4. TC 자체검증 체크리스트 (Phase 3.5 — 기준문서가 있는 경우에만 수행)

**적용 조건**: 이 단계는 §2의 기준문서(정책서/화면설계서/Figma/PRD/ERD 등)가 **존재하는 프로젝트에서만** 수행한다.

| 상황 | 처리 |
|---|---|
| 기준문서 **있음** | 아래 체크리스트를 Phase 3 승인 후 ~ Phase 4 착수 전에 전 TC에 대해 수행 |
| 기준문서 **없음** | 이 단계를 **생략**한다. 대신 §3의 예외 처리 원칙(근거 불확실 시 `[확인필요]` 태그 + P3 고정)을 TC 작성 시점에 기본 적용하는 것으로 갈음한다 |

기준문서가 있을 때, 각 TC 작성 후 아래 체크리스트를 **모두 통과해야 HTML 뷰어에 포함**한다.

```
[ ] 1. 이 TC의 진입 경로가 Figma/PRD/캡처화면에 존재하는가?
[ ] 2. Platform(App/Web)이 메뉴트리와 일치하는가?
[ ] 3. Out of scope에 포함되지 않는가?
[ ] 4. Procedure만 보고 QA가 즉시 실행 가능한가?
[ ] 5. Expected result가 검증 가능한 구체적 값/상태인가?
[ ] 6. 근거(Figma/PRD/ERD/Slack/캡처화면)를 댈 수 있는가?
```

- **하나라도 X**이면: 해당 TC를 사용자에게 체크리스트와 함께 제시하고, 질의를 통해 확인받은 뒤 **"TC 삭제"** 또는 **"[확인필요] 태그 부착(§3 예외 처리 적용)"** 중 하나로 처리한다.
- 결과를 간단한 검증 요약(통과/삭제/확인필요 건수)으로 사용자에게 보고한다.

## 6. 사전조건 작성 규칙 (★ 초보자 기준)

- **원칙: 기대결과를 얻기 위해 절차 수행에 실제로 필요한 항목만** 남긴다. 불필요한 나열 금지.
- 회원유형/계정 정보가 결과에 영향을 주지 않는 케이스(상품 데이터 정합성, 검색/리스트, 가격비교, 접근성, 크로스브라우저, 보안 취약점 점검, 성능 등)는 **계정 정보 자체를 넣지 않는다.**
  - 판단 기준: 모듈이 로그인/마이페이지/주문결제/취소반품/결제보안/정기구독/해외직구/프로모션/멤버십에 해당하거나, 시나리오에 "로그인/비회원/멤버십/쿠폰/포인트/구매확정/동기화/배송지"가 언급될 때만 계정 정보 포함.
  - 남길 항목이 없으면 `특이 사전조건 없음` 한 줄로 표기.
- 계정 정보를 넣을 때는 **하나로 뭉치지 말고 세분화**하여 번호를 매긴다:
  ```
  1) Acc_Normal (네이버 통합회원)
  2) 결제수단 : 등록카드 1개 - 신한카드
  3) 보조결제수단 : 포인트 0P 보유
  4) 쿠폰 : 0개 보유
  5) 배송지 : 기본배송지 서울 강남구 등록
  ```
- 값이 "0개/0P/없음" 등 **기본값이고 해당 시나리오와 무관하면 그 줄 자체를 숨긴다.**
- 검증도구(개발자도구/프록시 등) 안내는 사전조건이 아니라 **절차(11번)로 이동**시킨다.
- "특이조건 :" 같은 라벨은 붙이지 않고 내용만 적는다.
- 항목이 2개 이상이면 절차와 동일하게 `1) 2) 3)` 넘버링한다.
- **글로벌/역직구 서비스**의 경우 계정 매트릭스에 배송국가/차단지역 축을 반드시 포함한다(예: Acc_Guest, Acc_Member, Acc_Member_ShipCountry, Acc_BlockedRegion, Acc_Member_Grade). 국내 단일국가 서비스는 이 축을 생략한다.

## 7. 테스트 절차 작성 규칙 — TC 유형별 구체화 (★ 초보자 기준)

공통 원칙: 화면 진입 단계는 추상적으로 쓰지 않는다.
- 로그인 필요: `계정 로그인 후 {화면명} 진입`
- 로그인 불필요(비회원 등): `{화면명} 진입`
- "사전조건 계정으로 관련 화면 진입" 같은 모호한 문구 금지.

### 7-1. UI TC
- 진입 경로를 명확히 명시한다. 예: `"Trade > Perp > Positions 진입 → TP/SL Set 클릭"`
- 검증 요소는 구체적으로 쓴다: 버튼 라벨 원문, 색상(Hex, 근거 있을 때만), 위치, 문구 원문.

### 7-2. API TC
- 검증 도구를 플랫폼별로 명시한다.
  - Web: `"브라우저 개발자 도구 > Network 탭"`
  - App: `"Charles / Proxyman / mitmproxy 등 프록시 도구"`
- 확인할 request URL(엔드포인트 원문)
- 확인할 request body 필드(필드명 + 예상값)
- 확인할 response 필드
- HTTP status code 확인
- 개발자도구 진입 방법 자체는 절차의 별도 보조설명(`*`)으로 분리한다 (§7-6 참조).

### 7-3. Network(성능/예외) TC
- 재현 방법을 플랫폼별로 명시한다.
  - Web: `"DevTools > Network > Offline 체크"` / `"Throttling: Slow 3G"`
  - App: `"기내모드 ON"` / `"Wi-Fi 끄기"`
- 어느 요청이 실패하는지 실패 지점을 명시한다.
- UI 반응(예외 모달/Skeleton UI 등) 확인 방법을 명시한다.

### 7-4. 상태 전이 TC
- 초기 상태를 어떻게 만드는지 구체적 세팅 방법을 쓴다.
- 트리거 방법(어떤 동작으로 상태가 바뀌는지)을 쓴다.
- 최종 상태를 어떻게 검증하는지 방법을 쓴다.

### 7-5. 회귀 TC
- 기존 시나리오 재현 절차를 쓴다.
- 신규 기능 도입 후 변경 여부를 확인할 포인트를 명시한다.
- 설정값(배송지/통화/언어/등급 등) 변경이 다른 화면(장바구니/위시리스트/쿠폰)에 미치는 **교차 영향**을 우선적으로 다룬다(§11-4 참조).

### 7-6. 개발자도구/프록시 안내 축약 형식 (전체 유형 공통)
개발자도구·프록시 도구가 필요한 단계는 **핵심 동작 1줄(번호 있음) + 보조설명 1줄(번호 없음, `*` 접두)**로 분리한다.
```
1) 개발자도구 실행 후 상단의 'Network' 탭 선택
    * 화면에서 마우스 오른쪽 버튼 클릭 → '검사(Inspect)' 선택(또는 키보드 F12 키)
```

## 7.5 컬럼 간 역할 분리 (★★★ 신규 — 테스트항목/사전조건/절차/기대결과 중복 서술 금지)

동일한 문장이 테스트항목→사전조건→절차→기대결과에서 형태만 바뀌어 반복되는 것은 대표적인 저품질 TC 패턴이다. 4개 컬럼은 아래와 같이 **서로 배타적인 정보만** 담는다.

| 컬럼 | 담아야 할 정보 | 담으면 안 되는 정보 |
|---|---|---|
| 테스트 항목(시나리오) | 소분류 이하 **검증 구분값** — "무엇을 검증하는가"를 명사형으로, 보통 "~검증"으로 끝맺음 | 구체적 액션(클릭/입력), 결과 문구, 절차 나열 |
| 사전조건 | 절차 수행 **전에 미리 세팅되어 있어야 하는** 환경·데이터 상태(계정유형 + 구체적 데이터 상태값) | 동작 동사("~클릭한다", "~진입한다" 등 절차에 속하는 표현) |
| 테스트 수행 절차 | 테스터가 **실제로 수행하는 액션**을 번호로 나열(클릭 대상/입력값을 구체적으로 명시) | 결과 서술("~노출된다", "~반영된다" 등은 기대결과의 영역) |
| 기대 결과 | 절차 각 번호에 대응하는 **시스템의 관찰 가능한 반응**(문구 원문, 상태 변화, 리다이렉트 등 절차·항목과 다른 새로운 정보) | 절차·테스트항목 문장을 형태만 바꿔 재진술(예: "~이 확인된다"로 제목을 그대로 반복) |

**작성 순서(권장)**: ① 사전조건(세팅값) → ② 절차(액션만) → ③ 기대결과(절차 번호별 반응, 절차에 없던 새 정보) → ④ 테스트항목(①~③을 압축한 검증 대상명, 마지막에 작성하면 중복이 줄어든다)

**Before/After 예시**
```
[중복 발생 예 - 지양]
테스트항목: 옵션 선택 시 가격/이미지 갱신
사전조건 : Acc_Guest
절차     : 1) PDP 진입 2) 옵션 선택 동작 수행
기대결과 : 옵션 선택 시 가격/이미지 갱신이 확인된다      ← 테스트항목 재진술, 정보 추가 없음

[역할 분리 예 - 지향]
테스트항목: 옵션 선택 시 가격·대표이미지 실시간 반영 검증
사전조건 : Acc_Guest, 옵션별 상이한 가격/이미지가 설정된 상품
절차     : 1) PDP 진입 2) Type 드롭다운에서 특정 옵션 선택
기대결과 : 1) 선택 옵션에 대응하는 가격으로 즉시 갱신됨 2) 대표 이미지가 옵션에 매칭된 이미지로 전환됨
```
- 절차와 기대결과는 **번호를 1:1로 대응**시킨다(절차 2번 액션의 결과는 기대결과 2번에 쓴다).
- 기대결과 작성 후, 테스트항목·사전조건과 문장이 70% 이상 겹치면 재작성한다(자체 점검 기준).

## 8. 기대결과 작성 규칙 (★ 구체적 값/상태 + 확인필요 분리)

§7.5의 역할 분리 원칙을 전제로, 아래 세부 규칙을 추가로 따른다.

- 본문은 "무엇이 검증되어야 하는가"를 **검증 가능한 구체적 값/상태**로 서술한다. 막연한 "정상 동작해야 한다" 수준의 서술은 지양하고, 가능한 한 필드명·예상값·상태값을 구체적으로 적는다.
- **Hex 코드, Bold, strikethrough, opacity% 등 CSS 상세 수치**는 근거(캡처화면/Figma)가 있을 때만 본문에서 분리하여 하단에 `* ` 보조설명(빨간색)으로 별도 표기한다. 근거 없이 임의의 Hex 값을 지어내지 않는다.
  ```
  구매 관련 버튼이 비활성화(Disabled) 상태로 노출되며, 클릭 시 "옵션을 선택해주세요" 안내 문구가 노출된다.
  * 비활성화 버튼 배경색 : Hex #D1D5DB   ← 빨간색 (근거: Figma frame #47:894)
  ```
- **정책 미문서화로 확인이 필요한 사항**도 동일하게 본문에서 분리하여 `* ` 보조설명(빨간색)으로 표기한다. `[확인필요]` 배지는 사용하지 않되(§3의 제목 태그와는 별개), TC 제목에는 §3 규칙에 따라 `[확인필요]`를 붙인다.

### 좋은 API TC 예시 (참고용)
```
사전조건 & 절차:
1) Advanced TP/SL 모달에서 Input=ROI, ROI=-10 입력 후 Confirm
2) 개발자 도구 > Network 탭 > POST /api/v2/trade/one-way/partial-tpsl/{symbol} 요청 클릭
3) Payload 탭에서 request body 필드 확인

기대결과:
1~3. Request body:
     - side: "Long"
     - orderQty: "0.5" (문자열)
     - triggerPrice: "59400.0"
     - triggerDirection: "Down"
     - executionType: "Market"
     - roi/pnl 필드 없음 (client-side conversion 원칙)
     - orderTp*/orderSl* prefix 없음 (One-way는 flat 구조)
```
이 예시처럼 **필드명 + 예상값 + 원칙(왜 그런 구조인지)**까지 구체적으로 적는 것을 목표로 한다.

## 9. Phase 4 — Interactive HTML 뷰어 스펙

- **탭 UI**: 상단에 "전체 + 모듈별" 탭을 두어 TC 리스트를 모듈 단위로 필터링할 수 있게 한다.
- **테마 토글**: 다크/라이트 모드 실시간 전환.
- **KPI 카운터**: 전체/P1/P2/P3 (현재 선택된 탭 기준으로 실시간 갱신).
- **모듈별 실행현황 통계표**: Pass/Fail/Blocked/N/A/미실행 건수와 함께 **수행율(=(Pass+Fail+Blocked+N/A)/전체), Pass율(=Pass/수행건수), Fail율(=Fail/수행건수)**을 모듈별로 집계하는 표를 KPI 카운터 **상단**에 배치, 실행결과 변경 시 실시간 갱신. 전체 합계 행도 함께 표기한다.
- **CSV 다운로드 버튼**: 현재 필터링된(또는 전체) TC 리스트를 CSV로 다운로드할 수 있는 버튼을 제공한다. 16개 컬럼(실행결과/담당자/이슈내용/이슈링크 포함) 전체를 내보내며, UTF-8 BOM을 포함해 엑셀에서 한글이 깨지지 않게 한다.
- **JSON 저장 버튼 (★ 신규)**: 현재 TC 데이터 전체(16개 컬럼 + 실행결과/담당자/이슈내용/이슈링크의 현재 입력값 포함)를 `.json` 파일로 다운로드한다.
  - 파일명 규칙: `{프로젝트명}_tc_{YYYY-MM-DD}.json`
  - 최상위 구조에 메타정보를 포함한다: `{ "meta": {"project":..., "generatedAt":..., "totalCount":...}, "items":[ {16개 컬럼 + 실행결과/담당자/이슈내용/이슈링크}, ... ] }`
  - CSV와 달리 JSON은 **재불러오기(다음 항목)를 전제로 한 원본 데이터 포맷**이므로, 필터링 여부와 무관하게 항상 **전체 TC**를 저장한다(부분 저장 시 재불러오기 때 데이터 유실 위험이 있으므로 금지).
- **JSON 불러오기 버튼 (★ 신규)**: 파일 선택(`<input type="file" accept=".json">`)으로 위 형식의 JSON을 업로드하면, 서버 전송 없이 브라우저 내 `FileReader`로 읽어 **뷰어에 즉시 반영**한다(테이블/탭/KPI/통계표 자동 재렌더링).
  - 불러온 데이터는 기존 하드코딩된 TC 데이터를 **대체**하며, 실행결과/담당자/이슈내용/이슈링크 값도 JSON에 저장된 값 그대로 복원한다(작업 이어하기 지원).
  - 형식이 맞지 않는 파일(필수 컬럼 누락, JSON 파싱 실패 등)을 업로드하면 **에러 메시지를 노출하고 기존 데이터는 유지**한다(잘못된 업로드로 화면이 빈 상태가 되지 않도록 방어).
  - 불러오기 성공 시 "OOO건 불러옴" 형태로 결과를 안내한다.
  - 용도: (1) 팀원 간 진행상황 공유(담당자가 실행결과 채운 JSON을 저장→전달→다른 PC에서 불러오기), (2) §13 배치 생성 중간 산출물 보관, (3) 새로고침으로 인한 메모리 데이터 유실에 대한 백업/복구.
- **테이블 가로 스크롤 금지**: `table-layout:fixed` + 컬럼별 % 폭 고정(합계 100%) + 텍스트 줄바꿈(`word-break:break-word`)으로 페이지 폭에 맞춘다. 세로 스크롤도 제거(전체 TC가 페이지 스크롤로 펼쳐지게).
- **모달 2종**: 테스트 계정 매트릭스, User Flow Map(회원유형별 5단계는 **표 형식**으로 제시).
- 13~16번 컬럼(실행결과/담당자/이슈내용/이슈링크)은 브라우저 메모리에만 저장됨을 하단에 명시하되, **JSON 저장/불러오기로 영구 백업 및 복원이 가능함을 함께 안내**한다(새로고침 시 초기화, CSV는 백업용 읽기전용 내보내기, JSON은 재불러오기 가능한 작업 파일).

## 10. HTML/JS 생성 시 필수 버그 방지 및 검증 규칙 (★ 중요)

과거 이스케이프 처리 오류로 스크립트 전체가 깨져 TC가 0건으로 렌더링된 사고가 있었다. 이를 방지하기 위해:

1. **인라인 `onclick`/`onchange` 문자열 조합 금지.** 반드시 `data-id` 속성 + `addEventListener` 방식(이벤트 위임)으로 구현한다.
2. TC 데이터(JSON)는 별도 생성 스크립트(Python 등)로 구조화 생성 후 HTML 템플릿에 삽입하는 방식을 권장한다(수작업 문자열 조합보다 이스케이프 오류 위험이 낮음).
3. HTML 생성 후 **`node --check`로 JS 구문 검증**을 반드시 수행한다.
4. **jsdom으로 런타임 시뮬레이션**을 수행하여 아래 항목을 모두 확인한다(사용자에게 결과를 표로 보고):
   - 초기 렌더링 시 전체 TC 건수 일치
   - 모듈 탭 클릭 시 필터링된 건수 일치, 전체 탭 복귀 시 원복 확인
   - 실행결과(Pass/Fail/Blocked/N/A) 변경 시 통계표 실시간 갱신 확인
   - 자유입력(담당자/이슈내용/이슈링크) 저장 확인
   - CSV 다운로드 버튼 클릭 시 오류 없음 확인
   - **JSON 저장 버튼 클릭 시 오류 없음 확인, 저장된 JSON의 `items` 길이가 전체 TC 건수와 일치하는지 확인**
   - **JSON 불러오기: (a) 정상 JSON 업로드 시 테이블·탭·통계표가 해당 데이터로 재렌더링되는지, (b) 실행결과/담당자 등 입력값이 그대로 복원되는지, (c) 잘못된 형식 업로드 시 에러 처리되고 기존 데이터가 유지되는지 3가지 모두 확인**
   - 테마 토글 동작 확인
   - 모달 2종 열기/닫기 확인
5. "확인은 했으나 검증하지 못한 부분"(예: 실제 브라우저 다운로드 완료, 반응형 레이아웃)과 "확인한 부분"을 답변에서 명확히 구분해 보고한다.

## 11. TC 확장 기법 (★ 신규 — 대규모/고도화 커버리지 확보)

목표 건수(150~200건+)를 채울 때, **근거 없는 화면을 새로 상상해서 늘리지 않는다.** 대신 이미 확보한 근거(캡처화면/정책문서)를 아래 5가지 기법으로 체계적으로 전개한다.

| 기법 | 설명 | 적용 예 |
|---|---|---|
| 상태값 전개 | 확보된 UI 요소가 가질 수 있는 실제 상태값들을 각각 TC로 분리 | 배송지 60개국 중 허용국/차단국 대표 케이스 |
| 경계값(Boundary) | 캡처된 실제 최소/최대값, 0/1 등 경계 조건 | 가격 슬라이더 최소~최대, 수량 1 미만 차단 |
| 조합(Combination) | 캡처된 필터/옵션 UI들을 2~3개씩 동시 적용 | 카테고리+브랜드+가격 필터 동시 적용 |
| 예외(Exception) | 확보된 정책 문구 기반의 실패/제한 케이스 | 쿠폰 최소금액 미충족, 결제 거절 |
| 회귀(Regression) | 한 화면의 설정 변경이 다른 화면에 미치는 교차 영향 | 배송지 변경 → 장바구니 금액/배송가능여부 재검증 |

- 이 5가지 기법 모두 **"이미 캡처/문서로 확인된 요소의 재조합"**이므로 §3 근거 원칙을 위반하지 않는다. 새로운 화면 요소를 상상해서 만드는 것과 명확히 구분한다.
- 확장 시에도 모듈별 배분표(Phase 3)를 먼저 제시하고 승인받은 뒤 세부 전개한다.

## 12. 데이터 정합성 검증 (★ 신규 — 품질·비기능 표준 카테고리)

근거 확보(§1) 과정에서 **동일 정보가 페이지마다 다르게 표기**된 경우(예: 무료배송 기준이 메타태그와 배너에서 다름), 이를 누락하지 않고 아래와 같이 별도 카테고리로 등록한다.

- 대분류: `품질·비기능`, 소분류: 발견된 항목명(예: 무료배송기준, 통화표기 등)
- 우선순위: 실서비스 정책 오류 가능성이 있으므로 기본 **P1**
- 절차: 발견된 두 소스를 모두 명시하고, 실제 적용되는 값을 실측 검증하는 절차로 작성
- 이런 발견은 QA 관점에서 가치가 높으므로, 발견 즉시 사용자에게 별도로 강조 보고한다.

## 13. 대규모 생성 진행 프로세스 (★ 신규 — 150건 이상)

1. **Phase 3에서 모듈별 목표 건수 배분표**를 먼저 제시하고 승인받는다(전체 건수 + 모듈별 건수 + 우선순위 예상 분포).
2. 세부 TC는 **50~65건 단위 배치**로 나누어 순차 전달한다. 매 배치 시작 전 진행 체크리스트를 갱신해 보여준다.
   ```
   ☑ Batch 1 (완료된 모듈들) — N건
   ☑ Batch 2 (완료된 모듈들) — N건
   □ Batch 3 (예정 모듈들) — N건
   □ Phase 4 (HTML 뷰어)
   ```
3. 사용량 한도 등으로 대화가 중단될 수 있음을 인지하고, **재개 시 마지막으로 완료된 배치 다음부터 자동으로 이어서 진행**한다(사용자가 별도로 지시하지 않아도 진행 상태를 스스로 파악해 이어간다).
4. 전 배치 완료 후 최종 집계표(배치별 건수, 우선순위 분포 합계)를 보고한 뒤 Phase 4로 진행한다.

## 14. 진행 시 커뮤니케이션 원칙

- 매 단계 시작 전 "이번 작업에서 진행할 내용"을 먼저 안내한다.
- 표/체크리스트 우선, 장문 설명 지양.
- 산출물 생성 후에는 근거(무엇을 검증했는지)를 함께 제시한다.
- 대규모 확장(예: TC 건수 증가)은 반드시 재승인을 받는다. 단, §0-4에 따라 최초 협의 시점에 목표 규모를 먼저 논의해 재승인 왕복을 최소화한다.
- Phase 3.5(자체검증)에서 삭제/확인필요 처리된 TC가 있으면, HTML 생성 결과 보고 시 함께 요약한다.
- 근거 확보 과정에서 접근 실패(robots 차단 등)나 데이터 불일치를 발견하면 즉시, 투명하게 보고한다 — 이를 숨기고 임의로 진행하지 않는다.
