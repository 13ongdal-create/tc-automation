TC 자동화 시스템 개요

Slack에서 프로젝트 단위로 TC(테스트 케이스)를 요청하면 Claude Code가 정책서/화면을 근거로 케이스를 설계하고, 승인 후 Playwright로 직접 실행까지 마치는 시스템입니다. 아래는 이 시스템을 처음 보는 동료에게 설명하기 위한 구조·프로세스·사용법 정리입니다.

운영 채널: #tc-automation 봇 이름: 큐돌이 저장소: tc-automation (Git) 버전: v0.2

01 토큰 사용 영역 및 기능

Claude를 실제로 호출(=비용 발생)하는 기능과, 코드만으로 처리되어 호출하지 않는 기능을 나눴습니다. 결정적으로 정형화할 수 있는 작업은 전부 토큰을 쓰지 않도록 설계되어 있습니다.

기능토큰이유
/tc-generate TC 생성 (Phase 1~4) 사용 정책서·화면 분석, 시나리오 설계 등 실제 추론이 필요한 핵심 기능
승인 후 자동화 테스트 실행 + git 커밋 사용 Claude가 테스트 실행·결과 해석·커밋 메시지 작성까지 수행
@큐돌이 자연어 멘션 (의도 판별) 사용 자유 텍스트에서 TC 생성/결함조회 의도와 프로젝트명을 추출해야 함
스레드 내 자유 수정요청 / 승인 / 반려 사용 실제로 TC를 다시 쓰거나 다음 단계로 진행해야 함
결함관리 중 자유 형식 질문 (예: "이 결함 원인이 뭐야?") 사용 (지연 시작) 정형 패턴에 안 걸릴 때만, 그 시점에 처음 세션을 엶
/tc-defects 최초 결함 현황 조회 미사용 defects.json 집계 후 표로 정리 — 브릿지 코드가 직접 처리
결함 담당자·상태·이슈링크 변경 (정형 문장) 미사용 defectFastPath.js 정규식 매칭 후 파일 직접 수정
상태 / 진행상황 조회 미사용 이미 실행 중인 프로세스의 스트리밍 출력에서 마지막 작업만 추출
중단 미사용 실행 중인 프로세스를 종료하는 것 뿐, Claude 호출 없음
웹훅 알림 4종 (크래시 / 연결끊김 / 개별오류 / is_error) 미사용 순수 프로세스·네트워크 이벤트이거나 이미 나온 결과를 재전송하는 것뿐

02 신규 프로젝트 TC 요청 → 실행 프로세스

프로젝트 온보딩부터 결함 등록까지 이어지는 전체 흐름입니다. 굵게 표시된 지점은 사람의 "승인"이 있어야만 다음 단계로 넘어갑니다.

1
프로젝트 온보딩
tc-automation/_template/을 project/{프로젝트명}/으로 복사 (Policy·SB·Requirements·TC). 다른 프로젝트를 복사하거나 참고하지 않음.
2
근거 자료 투입
정책서→Policy, 화면설계서→SB, 요구사항→Requirements, 기존 TC→TC/legacy
3
Slack에서 요청
/tc-generate 프로젝트=X 모듈=Y 또는 URL 포함, 또는 @큐돌이 자연어
4
Phase 1~3 — 근거 확보 & 시나리오 검토표
정책서 분석 또는 URL 관찰(Playwright) → 계정 매트릭스/User Flow → 시나리오 검토표 제시
⏸ 1차 승인 대기
5
Phase 3.5~4 — 자체검증 & TC 산출물 생성
TC HTML/JSON 뷰어 생성. URL 기반이면 Playwright 테스트 코드도 함께 생성
⏸ 2차 승인 대기
6
테스트 실행 & 커밋
Playwright 자동화 테스트 실행 → 콘솔 에러/실패 감지 시 스크린샷 캡처 → 결과 리포트
✅ 통과: 실행결과 반영 후 git add {프로젝트명} → commit → push
❌ 실패: defects.json에 결함 자동 등록/갱신 (재발생 시 상태 복원)
7
이후 결함 관리
/tc-defects 또는 스레드 내 자연어로 담당자 지정·상태 변경·재검증 지속

03 문서(MD) 관리 위치

규칙과 스펙은 4개 문서에 나뉘어 있습니다. 이 중 Git으로 관리되는 건 PIPELINE.md 하나뿐이라는 점을 04번에서 문제로 짚었습니다.

파일위치용도Git 관리
AGENTS.md .agents/AGENTS.md 전체 행동 규칙 (TC 스키마, 우선순위, 근거원칙, Git 규칙, URL 자동화, 결함관리 등 0~20항) 미관리
SKILL.md .agents/skills/qa-test-case-generator/SKILL.md TC 생성 스킬의 상세 실행 스펙 (컬럼 정의, Phase 워크플로우, HTML 뷰어 스펙) 미관리
role-definition.md .agents/skills/.../references/ 페르소나·역량·테스트 설계 기법 참조문서 미관리
PIPELINE.md tc-automation/_reference/PIPELINE.md Slack 연동 아키텍처, 발화 규칙, 토큰 최적화 정책 tc-automation repo
slack-bridge/README.md + 소스코드 slack-bridge/ 브릿지 서버 설치/운영 가이드 + 실제 봇 서버 코드 전체 미관리

04 알려진 문제·중복 프로세스

현재 구조를 점검하며 발견한 실제 이슈입니다. 심각도는 데이터 손실 가능성과 사용자 혼동 정도 기준입니다.

이슈심각도설명
행동 규칙(.agents)과 봇 서버 코드(slack-bridge)가 버전관리 안 됨 Critical 이 PC 디스크 장애 시 규칙·서버 코드 전체가 복구 불가. TC 데이터(tc-automation)만 Git으로 보호되고 있음
자연어 결함 요청은 fast-path 혜택을 못 받음 Medium @큐돌이 결함현황 보여줘처럼 자연어로 오면 /tc-defects와 같은 작업인데도 항상 토큰을 쓰고, 이후 담당자 변경도 fast-path 대상에서 빠짐
"승인" 키워드가 두 단계 게이트에 재사용됨 Minor 검토표 승인과 최종 실행/커밋 승인이 같은 문구라, "한 번 승인했는데 왜 또?"로 혼동 가능 (실제 문의 있었음)
defects.json 동시 수정 경합 가능성 Minor fast-path(코드)와 Claude(같은 파일)가 이론상 겹칠 수 있음. 실제로는 진행 중 상태 체크로 대부분 방지되나 완전한 락은 아님

05 사용자 워크플로우 (Slack 사용법)

새 요청을 여는 명령과, 열린 스레드 안에서 쓰는 답장으로 나뉩니다.

새 스레드를 여는 명령

/tc-generate 프로젝트=X 모듈=Y 목표건수=50
정책서 기반 TC 생성 요청
/tc-generate 프로젝트=X 모듈=Y URL=https://...
실제 화면 관찰(Playwright) 기반 + 승인 시 자동화 테스트까지 실행
/tc-defects 프로젝트=X
결함 현황 조회 (토큰 미사용, 즉시 응답)
@큐돌이 X 프로젝트 장바구니 TC 만들어줘
자연어 멘션 — 의도를 스스로 판별 (TC생성 vs 결함조회)

열린 스레드 안 답장

답장동작
승인 / approve다음 단계 진행 (검토표→생성, 생성→실행+커밋)
반려: 사유 / 거절: 사유사유 반영해 재작성, 커밋 안 함
자유 문장 (예: "쿠폰 케이스 더 추가해줘")내용 반영해 다시 제시
상태 / 진행상황지금 어떤 작업 중인지 즉시 응답 (토큰 미사용)
중단 / 취소실행 중인 프로세스 강제 종료
DEF_xxx 담당자를 홍길동으로 지정해줘결함 담당자 변경 (토큰 미사용)
DEF_xxx 완료 처리해줘결함 상태 변경 (토큰 미사용)
