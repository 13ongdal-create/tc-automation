## 1. 핵심 작성 철학 (Core Principles)

### ① FO(Front-Office) 친화성 및 텍스트 기반 명쾌화 원칙 (Junior-friendly Naming)
* **내부 코드 및 키값 단독 표기 금지**: `Acc_Island`, `Acc_Wow`, `Acc_Normal`, `Acc_Guest` 등 시스템 키값이나 내부 DB 코드만 단독으로 기재하면 초보 QA 및 협업 구성원이 테스트 데이터 세팅에 난항을 겪게 됩니다.
* **FO 화면 노출 텍스트 + (키값) 병기 필수**: 항상 사용자가 보는 FO 화면 상에 어떻게 나타나는지 **UI 명칭 및 상태를 텍스트로 풀어 쓴 뒤 괄호 안에 키값을 기재**해야 합니다.
  * ❌ *잘못된 예시*: "Acc_Wow로 접속하여 혜택가 확인"
  * ⭕ *올바른 표준*: "** 멤버십 가입 회원 (`Acc_Wow`)**으로 접속하여 혜택가 확인"

### ② 100% 실행 가능한 구체성 및 툴 활용 가이드 명세
* 모든 테스트 수행 절차와 기대 결과는 모호한 형용사("잘 뜬다", "정상적이다")를 배제하고, **구체적 수치, 색상 코드, API 응답 필드 및 HTTP 상태 코드, 오류 모달 문구 원문**을 1대1 매핑하여 기입합니다.
* Web 및 App의 통신 패킷 캡처 및 네트워크 가변 환경 설정을 위한 **구체적인 검증 도구 조작 경로(DevTools, Charles Proxy 등)를 반드시 절차 내에 명시**합니다.

## 2. 테스트 케이스 시트 표준 컬럼 규격 (Column Schema)

테스트 케이스 시트는 QA 담당자가 수행 흐름(시나리오 파악 → 유형 및 우선순위 인지 → 사전 조건 셋업 → 절차 수행 → 결과 검증)을 직관적으로 따를 수 있도록 아래의 고유 11개 컬럼 배치 구조를 100% 준수합니다.

| 1. TC ID | 2. 대분류 | 3. 중분류 | 4. 소분류 | 5. 플랫폼 | 6. 테스트 유형 | 7. 테스트 항목(시나리오) | 8. 우선순위 | 9. 사전 조건 | 10. 테스트 수행 절차 | 11. 기대 결과 |
| :---: | :---: | :---: | :---: | :---: | :---: | :--- | :---: | :--- | :--- | :--- |
| 식별 코드<br>(TC_PD_01) | 최상위 도메인<br>(상품상세) | 화면/모듈<br>(가격/혜택) | 그룹 단위 기재<br>([3] 가격, 혜택...) | PC / App | UI / 기능 / API / 성능 / 데이터 | 테스트 대상 명확히 작성 | P1 / P2 / **P3**<br>*(회귀/예외=P3)* | 실행 위한 계정, 툴 셋업 상태 | 구체적인 Numbering 절차 및 툴 조작 | 상태코드, 페이로드, FO 문구 원문 검증 |

### [컬럼 규격 상세 안내]
1. **TC ID**: 모듈별 약어로 지정 (예: 상품상세는 `TC_PD_00`, 메인은 `TC_MN_00`)
2. **대분류 / 중분류**: 서비스 대도메인(예: 상품상세, 메인페이지, 결제서)과 중단위 기능(예: 진입/로딩, 옵션/수량, 상단 GNB)
3. **소분류**: 대분류 및 중분류를 포괄하는 명확한 **그룹 항목 명칭**을 그대로 삽입 (예: `[1] 진입, 로딩 및 딥링크 (Entrance, Loading & SEO)`)
4. **플랫폼**: `PC`, `App`, `PC / App`
5. **테스트 유형 (5대 허용 규칙)**:
   * **`UI`**: 화면 렌더링, 색상, 레이아웃 정렬, CSS 하이라이팅, 마이크로 애니메이션, 팝오픈 뷰 모션
   * **`기능`**: 버튼 인터랙션, 드롭다운 옵션 조작, 탭 내비게이션 전이, 검색 바 입력 작동
   * **`API`**: 백엔드 REST API 통신 상태코드, JSON Payload 파라미터 무결성, DB 상태 값 동기화
   * **`성능`**: 로딩 속도, Lazy Loading, 레이턴시, CLS(누적 레이아웃 비틀림) 최적화, 메모리 유출(Crash) 방호
   * **`데이터`**: 금액 수식 산출, 할인율 반올림 계산, 고시 표기법 준수 여부, OG 메타 태그 무결성
6. **우선순위 (Priority 규칙)**:
   * **`P1 (Critical)`**: 구매 CTA 이관 차단, 가격 및 할인 계산 에러, 옵션 선택 불가 등 결함 발생 시 서비스 중단을 불사하는 최고 위험군
   * **`P2 (Major)`**: 리뷰 정렬 실패, Q&A 모달 오류, 보조 배너 링크 오류 등 사용성과 인지 가치를 낮추는 일반 기능군
   * **`P3 (Minor 및 예외/회귀 강제 할당 규칙)`**:
     * **[절대 준수 규칙]** 기능의 단순 오류를 넘어, **모든 회귀(Regression) 테스트 및 예외 처리(Exception / Boundary / Blocking) 시나리오는 우선순위를 P3로 정의**합니다. (정상 도메인 흐름과 차별화된 엣지 및 퇴장 방어성 테스팅에 뚜렷한 표식 부여 목적)
7. **사전 조건**: FO 명칭 기반 테스트 계정 셋업, 프록시 툴 / 네트워크 옵션 활성화 여부, 초기 데이터 장착 여부 명기

## 4. 5대 TC 세부 가이드북 (How to Write High-Precision Procedures)

### ① UI TC 작성 원칙
* **진입 경로 명명화**: ` 홈 > 검색 > '빠른배송 우유' 검색결과 > 대상 상품상세 진입 → [쿠폰 받기 ▽] 클릭`
* **시각 요소 수치 지정**: `적색 강조 글리프(#CB1400, Bold)`, `딤드(Dimmed: 회색 #F2F2F2 배경) 처리`, `천 단위 콤마(,) 및 원 표기 필수(예: 14,000원)`

### ② API TC 작성 원칙
* **검증 도구 명시**:
  * Web: `"브라우저 개발자 도구 (F12) > Network 탭 (XHR/Fetch 필터) ON"`
  * App: `"Charles Proxy / Proxyman 패킷 캡처 (SSL Slicing) 모니터링 활성화"`
* **핵심 페이로드 대조 (예시 구조)**:
  ```yaml
  Procedure:
    1. 상품 상세에서 수량을 2개로 조정 후 파란색 [장바구니 담기] 클릭
    2. DevTools > Network 탭 > POST /api/v2/cart/items (또는 장바구니 엔드포인트) 요청 선택
    3. Request Body 및 Response Payload 무결성 검증

  Expected Result:
    1~3. HTTP Status: 200 OK
         Request Body: {"vendorItemId": 85586788441, "quantity": 2, "itemSource": "PDP"}
         Response Body: {"resultCode": "SUCCESS", "cartTotalCount": 3}
         FO UI 변경: 상단 장바구니 카트 배지 텍스트가 즉시 3으로 애니메이션 변환됨.
  ```

### ③ Network (장애 감내 및 예외 핸들링) TC 작성 원칙
* **재현 방법 및 조각 지정**:
  * Web: `"DevTools > Network > Throttling > 'Slow 3G' 드롭다운 설정"` / `"Offline 체크박스 활성"`
  * App: `"스마트폰 상단 바 내려 기내모드(Airplane Mode) ON"` / `"Wi-Fi 및 셀룰러 데이터 OFF"`
* **Fallback UI 기대결과**: Broken Image(엑스 아이콘)나 App 크래시(OOM)가 날 것 그대로 터지는 것을 금지합니다. 반드시 **Skeleton UI (Shimmer 로딩 에보딩)** 혹은 친절한 예외 모달(**"네트워크 연결이 원활하지 않습니다 [재시도 ↻]"**)이 전개되는지 관전합니다.

### ④ 상태 전이 (State Transition) TC 작성 원칙
* **초기 상태 세팅 → 트리거 → 최종 데이터 동기화**:
  * 예: 즉시 3,000원 쿠폰이 미다운로드된 상태에서 **[쿠폰 받기]**를 누르면, 새로고침(F5) 없이 AJAX DOM 갱신만으로 상단 실결제 가액에 `-3,000원`이 즉석 공제 환산 표출되는 실시간 연계를 입증합니다.

### ⑤ 회귀 (Regression) TC 작성 원칙
* **신기술 및 비동기 광고 도입 시 부작용 차단**:
  * 비동기 프로모션 배너들이 나중에 팝인(Pop-in)되더라도 **DevTools > Performance > Web Vitals CLS(Cumulative Layout Shift, 누적 레이아웃 비틀림)가 0.1 미만으로 유지**되어 기존 버튼이 밑으로 내려앉는 참사를 검증합니다.
