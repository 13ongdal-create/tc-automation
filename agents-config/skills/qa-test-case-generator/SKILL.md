## 1. 근거 확보 절차 ★ (기준문서 없는 실서비스 대상 필수)

기준문서가 없는 경우, 추측으로 넘어가지 않고 아래 순서로 **실제 근거를 최대한 확보**합니다:

```
1순위. 대상 URL/파일을 직접 접근·분석
2순위. 하위 경로 다각도 시도 (상품상세/장바구니/정책페이지 등)
3순위. 검색으로 화면 스니펫/캡처 정보를 보조 근거로 수집
         (단, 이것만으로는 확인 필요 표시 유지)
4순위. 사용자에게 스크린샷 업로드 명시적 요청
         → 업로드된 이미지는 반드시 실제 내용 확인 후 근거로 사용
```

- 접근 성공/실패 여부와 관계없이 **시도 결과를 사용자에게 투명하게 보고**합니다
- **라이브 URL 기반 TC는 특정 상품ID·정확한 개수 등 계속 바뀌는 데이터를 하드코딩하지 않습니다** (임의의 유효 데이터로 검증하는 방식으로 일반화, AGENTS.md 20-8항 참조 — 2026-08-21 데모사이트에서 상품 판매종료로 다수 TC가 깨진 사례로 확정)
- 동일 정보에 대해 **페이지마다 다른 값** 발견 시(예: 무료배송 기준이 배너와 메타태그에서 다름) → 숨기지 않고 **데이터 정합성 TC(12. 데이터 정합성 검증)로 등록**합니다

## 3. TC 컬럼 스키마 (가변)

TC 컬럼은 프로젝트 요건에 따라 **유연하게 조정 가능**합니다. 기본 구성은 아래를 따릅니다.

| No | 컬럼 | 작성 규칙 |
|----|------|----------|
| 1 | **TC ID** | `TC_{모듈코드}_{3자리숫자}` (예: TC_PD_001) |
| 2 | **system** | `FO`(Front) / `BO`(Admin) — 프로젝트에 Front/Admin(Back-office)이 모두 존재할 때만 사용(19-2항 참조). Front만 있는 프로젝트는 전부 `FO`로 채웁니다 |
| 3 | **대분류** | 상품/구매프로세스/클레임/회원/전시/고객센터/품질·비기능/예외·회귀 등 |
| 4 | **중분류** | 모듈명 (예: 상품상세, 장바구니, 주문결제) |
| 5 | **소분류** | 세부 기능명 (예: 옵션선택, 수량정책, 귀책구분) |
| 6 | **화면명** | 해당 TC가 대상으로 하는 구체적 화면/페이지명 (예: 전시 대분류 아래 "MD's PICK", "메인", "베스트", "카테고리"). **대분류/중분류에 화면명을 괄호 병기하지 않고 반드시 이 컬럼에 별도로 기재**합니다 — 대시보드 등에서 모듈(대분류) 단위로 집계할 때 같은 모듈의 다른 화면이 별도 항목으로 쪼개지는 것을 방지하기 위함입니다(2026-08-26 확정, AGENTS.md 2항 공통 정책) |

| 9 | **테스트 항목(시나리오)** | "무엇을 검증하는가"를 명사형으로 — 보통 "~검증"으로 끝맺음. 불확실 시 `[확인필요]` 접두 |
| 10 | **기준문서** | `{파일명}_{버전}_{페이지}` 형식. 없으면 `-`. 재사용 패턴 적용 시 끝에 `· 패턴: {패턴명}` 추가 (AGENTS.md 11-1항) |
| 11 | **우선순위** | P1 / P2 / P3 |
| 12 | **테스트 데이터** | 수행에 필요한 구체적 입력값, 계정, API 파라미터, 샘플 데이터. **해당 없으면 빈 값**("특이 테스트 데이터 없음" 등 플레이스홀더 문구 금지 — 2026-08-20 수정) |
| 13 | **사전조건** | 절차 수행 전 미리 세팅된 환경·계정·데이터 상태값만 (동작 동사 금지) |
| 14 | **테스트 수행 절차** | 테스터가 실제 수행하는 액션, 번호 나열. 결과 서술 금지. 절차가 `system` 컬럼과 다른 시스템을 거치는 경우(19-2항 혼합 플로우) 해당 단계 앞에 `[FO]`/`[BO]`를 표기. **경로 대신 화면명으로 기입**(2026-08-21 수정, 3-2항 참조) |

### 3-1. system 컬럼 판정 기준

- **값의 의미**: 테스트 절차상 **최종적으로 기대결과를 확인/검증해야 하는 대상 시스템**을 기재합니다. 절차의 시작 지점이 아니라 **검증 지점** 기준입니다.
  - 예: BO에서 쿠폰을 발급하고 FO 마이페이지 쿠폰함에서 발급 여부를 확인하는 TC → 최종 검증은 FO에서 이루어지므로 `system = FO`.
- **혼합 플로우 표기**: 절차 중 일부 단계가 `system` 값과 다른 시스템에서 수행되는 경우, 그 단계에 한해 절차 문구 앞에 `[FO]` 또는 `[BO]`를 명시합니다 (예: `1) [BO] 관리자 > 쿠폰관리에서 쿠폰 발급 처리` `2) [FO] 마이페이지 > 쿠폰에서 발급된 쿠폰 노출 확인`).
- **적용 범위**: 이 규칙은 데모사이트 한정이 아니라 **향후 모든 프로젝트의 TC 생성에 동일하게 적용**되는 표준 컬럼 규칙입니다.

### 3-2. 절차/기대결과 표기 규칙 (2026-08-21 확정)

**정해진 목표 건수를 채우기 위해서가 아니라, 도출 가능한 최대치를 뽑아내기 위해** 아래 5가지 기법을 적용합니다. **근거 없는 화면을 상상해서 늘리지 않습니다** — 늘어난 개수는 항상 실제 근거(정책서/화면/기존 TC 패턴)에서 나와야 합니다.
이미 확보한 근거를 아래 5가지 기법으로 체계적으로 전개합니다:

| 기법 | 설명 | 적용 예 |
|------|------|---------|
| **상태값 전개** | UI 요소가 가질 수 있는 실제 상태값들을 각각 TC로 분리 | 배송 상태: 결제완료/배송중/배송완료/취소/반품 |
| **경계값(Boundary)** | 실제 최소/최대값, 0/1 등 경계 조건 | 수량 1 미만 차단, 최대 99개 초과 |
| **조합(Combination)** | 필터/옵션 UI들을 2~3개씩 동시 적용 | 카테고리+브랜드+가격 필터 동시 적용 |
| **예외(Exception)** | 정책 문구 기반의 실패/제한 케이스 | 쿠폰 최소금액 미충족, 결제 거절 |
| **회귀(Regression)** | 한 화면 설정 변경이 다른 화면에 미치는 교차 영향 | 배송지 변경 → 장바구니 배송비/가능여부 재검증 |

## 12. 데이터 정합성 검증 ★ (품질·비기능 표준 카테고리)

근거 확보 과정에서 **동일 정보가 페이지마다 다르게 표기**된 경우:

- **대분류**: `품질·비기능`, **소분류**: 발견된 항목명 (예: 무료배송기준, 통화표기)
- **우선순위**: 실서비스 정책 오류 가능성이 있으므로 기본 **P1**
- **절차**: 발견된 두 소스 모두 명시, 실제 적용값을 실측 검증하는 절차 작성
- 발견 즉시 사용자에게 별도로 **강조 보고**합니다

1. **인라인 `onclick`/`onchange` 문자열 조합 금지** → `data-id` + `addEventListener` (이벤트 위임)
2. TC 데이터(JSON)는 구조화 생성 후 HTML 템플릿에 삽입
3. HTML 생성 후 **JS 구문 검증** 수행
4. jsdom 시뮬레이션 확인 항목:
   - 초기 렌더링 TC 건수 일치
