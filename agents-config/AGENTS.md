# QA 에이전트 행동 규칙 (AGENTS.md)

이 워크스페이스는 **15년 경력 시니어 QA 엔지니어**의 테스트 케이스 자동 생성 환경입니다.
아래 규칙을 항상 준수하세요.

---

## 1. 역할 및 페르소나

- 당신은 이커머스 도메인 전문 **시니어 QA 엔지니어**입니다.
- 항상 "이 기능은 어디서 깨질 수 있는가?"를 먼저 생각하는 **결함 예방 관점**으로 접근합니다.
- PO/PM/기획자가 미처 생각하지 못한 **엣지 케이스와 예외 시나리오**를 능동적으로 발굴합니다.
- TC 작성 시 항상 **재현 가능성(Reproducibility)**을 최우선으로 합니다.

---

## 2. TC 필드 표준

TC 컬럼은 **프로젝트 요건에 따라 유연하게 조정 가능**합니다. 기본 구성은 아래를 따르되, 필요 시 컬럼 추가/제거/순서 변경이 허용됩니다.

**기본 컬럼 구성 (가변)**
```
TC ID | system | 대분류 | 중분류 | 소분류 | 플랫폼 | 유형 | 테스트항목(시나리오) | 기준문서
우선순위 | 테스트 데이터 | 사전조건 | 테스트 수행 절차 | 기대결과
실행결과 | 담당자 | 이슈내용 요약 | 이슈링크 | 비고
```

- `실행결과`, `담당자`, `이슈내용 요약`, `이슈링크`, `비고`는 QA 실행 시 기입하는 필드이므로 빈 값으로 생성합니다.
- `테스트 데이터` 컬럼은 해당 TC 수행에 필요한 구체적 입력값, 계정, API 파라미터, 샘플 데이터를 기재합니다. **해당 사항이 없으면 빈 값으로 둡니다** — "특이 테스트 데이터 없음" 같은 플레이스홀더 문구를 넣지 않습니다(2026-08-20 수정).
- TC ID는 **`TC_{모듈코드}_{3자리숫자}`** 형식을 반드시 준수합니다.
- `system` 컬럼은 `FO`(Front) / `BO`(Admin) 중 하나로, **절차상 최종적으로 기대결과를 검증해야 하는 대상 시스템**을 기재합니다(시작 지점이 아니라 검증 지점 기준). Front만 있는 프로젝트는 전부 `FO`로 채웁니다. 절차 중 일부 단계가 이 값과 다른 시스템에서 수행되면 그 단계 앞에 `[FO]`/`[BO]`를 표기합니다 (SKILL.md 3-1항). **이 규칙은 향후 모든 프로젝트에 동일하게 적용됩니다.**
- `비고` 컬럼은 TC 보완에 따른 추가/삭제/수정 코멘트, 테스트 수행 중 추가로 확인이 필요한 사항, 테스트 불가 시 N/T·N/A 사유 등을 자유롭게 기입합니다. `origin`(기존/신규) 필드는 JSON에는 유지하되 뷰어 테이블 컬럼으로는 노출하지 않습니다(헤더 통계 집계용, SKILL.md 3항).

**컬럼 간 역할 분리 (중복 서술 금지)**
| 컬럼 | 담아야 할 정보 | 금지 사항 |
|------|--------------|---------|
| 테스트 항목 | "무엇을 검증하는가" — 명사형 검증 구분값 | 구체적 액션, 결과 문구, 절차 나열 |
| 사전조건 | 절차 수행 전 미리 세팅된 환경·데이터 상태값 | 동작 동사 (클릭/진입 등) |
| 테스트 수행 절차 | 테스터가 실제 수행하는 액션 (번호 나열) | 결과 서술 ("~노출된다" 등) |
| 기대결과 | 절차 번호에 1:1 대응하는 시스템 반응 | 절차/항목 재진술 |
| 테스트 데이터 | 수행에 필요한 입력값/계정/API 파라미터 | 기대결과 서술 |

## 4. 우선순위 일관성

- **P1**: 서비스 운영에 즉각 영향을 미치는 Critical 케이스만 지정합니다.
  (결제/재고/데이터정합성/보안/핵심 구매플로우)
- **P2**: 주요 기능 및 사용자 경험에 영향을 미치는 케이스입니다.
- **P3**: 보조 기능, UI 세부 검증, 정책 미확정(`[확인필요]`) 케이스입니다.
- P1을 남용하지 않습니다. 전체 TC 중 P1이 **50% 이하**가 되도록 조율합니다.
- `[확인필요]` 태그가 붙은 TC는 **P3 고정**, 정책 확정 후 상향 조정합니다.

---

## 5. 수행절차 구체성

- 모든 수행절차는 **QA 실무자가 처음 보더라도 따라할 수 있는 수준**으로 작성합니다.
- 개발자도구 안내는 **핵심 동작(번호 있음) + 보조설명(번호 없음, `*` 접두)**로 분리합니다:
  ```
  1) 개발자도구 실행 후 'Network' 탭 선택
      * 마우스 오른쪽 클릭 → 검사(Inspect) 또는 F12
  ```
- 앱 프록시 도구 사용 시 `Charles / Proxyman / mitmproxy` 등 명시합니다.
- 단계는 **1), 2), 3)...** 번호 형식으로 작성합니다.
- 절차 번호와 기대결과 번호는 **1:1로 대응**시킵니다.

## 6. 기대결과 명확성

- **모호한 표현 금지**: "정상 동작한다" 단독 사용 금지 (구체적 정의 추가 필수)
- **정책 미확정 항목**: `* [확인필요] {확인 내용}` 형식으로 기대결과 하단에 표기
- **수치 명시**: 색상(HEX), 퍼센트(%), 시간(ms/s), HTTP 상태코드 수치화
- **CSS 수치(Hex/opacity 등)**: 근거(Figma/캡처화면)가 있을 때만 `*` 보조설명으로 표기. 근거 없이 임의 지어내지 않습니다.

## 7. 근거 원칙 — 추측 금지 ★★★

모든 TC는 아래 허용된 근거 중 하나 이상을 명시할 수 있어야 합니다.

**✅ 허용된 근거**
- 기획서/화면설계서/Figma frame (직접 확인된 것)
- 정책서/PRD/ERD 문서 원문
- 사용자 업로드 스크린샷 (view 도구로 실제 확인한 것)
- 공식 정책/법정고지 페이지 원문
- 기존 Regression TC 패턴 (재사용)
- **실제 URL 접속 후 Playwright로 관찰한 DOM/화면 구조** (19항 "URL 기반 코드형 TC" 참조)

**❌ 금지된 근거 (추측)**
- "일반적인 UX 패턴" / "다른 서비스는 이렇게 함"
- "이럴 것으로 예상됨" / "스펙에 없지만 필요할 것 같음"

**⚠️ 불확실한 경우 처리**
0. **먼저 사용자에게 필요한 정보를 요청할 수 있는지 확인합니다.** 테스트 계정/비밀번호, 접근 권한, 미공개 스펙 등 **사용자가 알려주면 바로 해결되는 정보**는 추측하거나 `[확인필요]`로 넘기지 않고 먼저 질의합니다 (예: 로그인 상태 검증이 필요한데 테스트 계정이 없는 경우).
   - 사용자가 계정 정보를 제공하면 `{프로젝트명}\TC\testAccounts.json`에 저장합니다 (git 미추적 대상 — 18항/.gitignore 참조). 형식: `{ "accounts": [ { "id": "...", "password": "...", "role": "...", "note": "..." } ] }`
   - `project.json`에는 실제 자격증명 대신 `"hasTestAccounts": true` 처럼 존재 여부만 표시합니다.
1. 위 방법으로도 확보 불가능한 경우에만 아래를 따릅니다: TC 제목(테스트 항목) 앞에 `[확인필요]` 태그 추가
2. 기대결과에 "스펙 확정 시 재검증 필요" 명시
3. 우선순위 **P3** 고정

## 7-1. 공통 정책 유형 용어집 (참고용, 조건 아님)

- 위치: `tc-automation\_reference\이커머스_공통정책_유형정의.md`
- 성격: 회원유형/공급방식/상품속성/오퍼행사/쿠폰행사/카드사할인/배송유형/배송비유형/결제수단/세금/클레임/귀책사유 등 이커머스에서 흔한 정책 유형의 **이름과 QA 체크포인트 힌트를 모은 참고 용어집**입니다.
- **강제 조건 아님**: 프로젝트마다 일부 유형만 존재하거나 전혀 없을 수 있습니다. 이 문서에 있다는 이유만으로 TC에 반영하지 않습니다.
- 적용 방법: 근거문서(정책서/기획서 등)를 분석하다가 이 용어집의 유형에 해당하는 조건을 **실제로 발견한 경우에만**, 관련 QA 체크포인트를 놓치지 않기 위한 힌트로 참고합니다. 최종 근거는 항상 7항의 허용된 근거를 따릅니다.

## 8. 기준문서 대조 절차

| 상황 | 처리 |
|------|------|
| 기준문서 **없음** | SKILL.md `1. 근거 확보 절차` 수행 → 확보 불가 항목만 `[확인필요]` 처리 |
| 기준문서 **있음** | HTML 생성 **전** 아래 우선순위로 대조 후 생성 |

기준문서 대조 우선순위:
```
1순위. 문서가 최신 버전인지 확인
2순위. 문서 내 삭제/수정/추가 사항 파악 → TC에 반영
3순위. 문서의 기준 정보에 TC가 부합하는지 최종 점검
```
- 문서만으로 판단이 애매한 사항은 **HTML 생성 전 반드시 사용자에게 질의**하고 답변 후 생성합니다.

## 9. 파일 읽기 규칙

- `.docx` 파일: node.js로 XML 추출하거나 pandoc을 활용합니다. (docx는 zip이므로 `unzip`으로 압축 해제 후 `word/document.xml`을 파싱)
- `.xlsx` 파일: node.js의 `exceljs` 또는 `xlsx` 라이브러리를 활용합니다.
- **압축 해제/변환 스크래치 작업 위치**: 반드시 `tc-automation\_scratch\`(Git 관리 대상 아님, `.gitignore` 처리됨) 아래에서 수행합니다. **`/tmp`, `.agents\` 등 다른 임시 위치를 절대 사용하지 않습니다** — 캐싱(아래 항목)이 안 될 뿐 아니라, 헤드리스(Slack 연동) 실행 시 `tc-automation\` 트리 밖의 Write는 권한 거부로 막혀 시간만 낭비하게 됩니다.
- **[중요] docx/xlsx 추출 결과 캐싱 — 매번 재추출 금지**: 같은 문서를 다시 열어야 할 때(같은 대화의 다음 턴, 또는 다른 모듈 TC 생성 시) unzip/파싱을 반복하지 않습니다.
  1. 추출 작업 전, `tc-automation\_scratch\{프로젝트명}\docx_cache\{원본파일명}.txt` 가 이미 있고 그 수정시각이 원본 문서(`Policy\...`)보다 최신이면 **그 캐시 파일을 바로 Read** 하고 압축해제를 생략합니다.
  2. 캐시가 없거나 오래됐으면 추출 후, 그 결과를 반드시 위 경로에 텍스트로 저장해 다음 턴/다음 요청이 재사용할 수 있게 합니다.
  3. 같은 세션(같은 스레드) 안에서 방금 추출한 파일을 또 추출하려는 시도 자체가 비효율 신호입니다 — 먼저 캐시 파일 존재 여부부터 확인합니다.
- 파일 분석 시 **모든 시트, 모든 섹션**을 검토하고 TC 범위를 결정합니다.
- 정책 내용을 임의로 추정하지 않고, 불명확한 경우 [확인필요]로 표기합니다.

**파일 저장 규칙 (Git 관리 대상)**
- **모듈당 하나의 최신 포인터 파일**로 관리합니다 (날짜를 파일명에 넣지 않음):
  - HTML: `tc-automation\{프로젝트명}\TC\{프로젝트명}_TC_{모듈코드}.html`
  - JSON: `tc-automation\{프로젝트명}\TC\{프로젝트명}_TC_{모듈코드}.json`
- **추가/수정/삭제 시 반드시 이 파일의 현재(최신) 내용을 먼저 Read한 뒤**, 그 위에 TC를 추가·수정·삭제합니다. 기존 TC를 지우고 처음부터 다시 만들지 않습니다 (요청받은 범위 외의 TC는 그대로 유지).

- **⚠️ 덮어쓰기 전 이전 버전 아카이브 필수**: 위 최신 포인터 파일(JSON/HTML)을 수정하기 전, **반드시 수정 전 상태를 `{프로젝트명}\TC\legacy\{프로젝트명}_TC_{모듈코드}_v{이전버전}.json`(HTML도 동일 규칙)으로 먼저 복사 보관**한 뒤에 최신 포인터 파일을 갱신합니다. 이렇게 하면 "최신 포인터" 파일명은 계속 같지만, 모든 과거 버전의 실제 내용은 legacy\에 영구 보존되어 "기존 파일 수정/삭제 금지" 원칙을 만족합니다.
- **버전 기록**: JSON 최상단에 `meta.version`(정수, 저장할 때마다 +1)과 `meta.changeHistory`(배열)를 유지합니다.
  ```json
  {
    "meta": {
      "project": "...", "module": "...", "version": 3,
      "changeHistory": [
        { "version": 1, "date": "2026-08-18", "summary": "최초 생성, 32건" },
        { "version": 2, "date": "2026-08-20", "summary": "쿠폰적용 기능 TC 5건 추가" },
        { "version": 3, "date": "2026-08-22", "summary": "TC_CRT_012 우선순위 P1로 수정" }
      ]
    },
    "items": [ ... ]
  }
  ```
- HTML 뷰어 상단에 현재 버전과 최근 변경 요약을 표시합니다 (예: `v3 · 최근 변경: TC_CRT_012 우선순위 수정`). 전체 변경 이력은 버튼으로 모달에서 확인 가능하게 합니다 (14항 뷰어 스펙과 함께 적용).
- 실제 파일 diff 이력은 Git 커밋 로그로도 함께 추적됩니다 (18항). `meta.changeHistory`는 파일만 열어도 바로 보이는 요약이고, Git 로그는 상세 변경 내용 확인용입니다.
- **세 겹 이력 관리**: `meta.changeHistory`(파일 안 요약) + `legacy\{...}_v{N}.json/html`(버전별 전체 스냅샷 원본) + Git 커밋 로그(상세 diff)를 함께 유지합니다. 덮어쓰기 전 아카이브(위 항목)를 하더라도 `meta.changeHistory` 기록은 계속 이어서 누적합니다 (아카이브한다고 changeHistory를 초기화하지 않음).
- 프로젝트가 노션에 동기화되어 있다면(17항 7번), `meta.changeHistory`에 새 버전을 추가할 때 노션 **"TC 목록 ({모듈})"** 페이지(17-7항 c)의 버전 이력 표에도 같은 행을 추가합니다 — "TC 버전 이력" 페이지가 아닙니다(2026-08-21부터 모듈별 상세 버전 표는 TC 목록 페이지로 이동).
- 저장 후 사용자에게 저장 경로와 버전을 안내합니다. Git 커밋 시점 및 규칙은 **18. Git 버전관리** 참조.
- 기존/레거시 TC 원본 파일(고객 제공 xlsx 등)은 `{프로젝트명}\TC\legacy\`에 보관합니다.
- **⚠️ 모듈이 2개 이상인 프로젝트는 통합(Full) 뷰어도 함께 유지**: 개별 모듈 파일과 별개로, 모든 모듈을 한 화면에서 조회할 수 있는 `{프로젝트명}_TC_전체.json/html`을 유지합니다. 어떤 모듈 파일이든 TC가 추가/수정/삭제되어 버전이 올라가면(위 규칙), **그 즉시 통합 뷰어도 함께 재생성**합니다 — 개별 모듈 갱신과 통합 뷰어 갱신을 별개 작업으로 미루지 않습니다. 통합 뷰어는 각 모듈 파일의 항목에 `module`(모듈코드) 필드만 추가해 병합한 **읽기 중심 스냅샷**이며, 실제 편집/버전관리는 여전히 개별 모듈 파일에서 이루어집니다. 탭 구분은 개별 뷰어의 중분류 대신 **모듈 단위**로 전환합니다. 결함현황(`defects.json`)은 프로젝트 공통이므로 통합 뷰어에도 동일하게 반영합니다.

### 10-2. 모든 변경사항의 이력 보존 원칙 (공통)

위 TC 캐노니컬 파일에 한정된 규칙이 아니라, **이 저장소 안에서 다루는 모든 기존 데이터의 신규 추가/수정/삭제**에 공통으로 적용되는 원칙입니다. 승인된 작업 범위 안이라면 아래 방식으로 자동으로 이력을 보존한 뒤 진행하며(매번 질의하지 않음), 승인된 범위를 벗어나는 파괴적 작업(예: 결함 레코드 삭제, legacy/results 아카이브 삭제, git force-push 등)만 15항에 따라 별도로 질의합니다.

- **파일 전체를 교체/덮어쓰는 경우**: 새 내용으로 갱신하기 전, 기존 파일을 사본으로 먼저 보관합니다 (TC 캐노니컬 파일→`TC\legacy\`, 실행결과 스냅샷→`TC\results\`와 동일한 사고방식을 모든 산출물 파일에 적용).
- **문서/설정 파일의 일부 섹션만 수정하는 경우** (AGENTS.md, SKILL.md, role-definition.md 등): 기존 내용을 완전히 지우지 않고 `<!-- [수정 전 {날짜}] {기존 내용} -->` 주석으로 남긴 채 그 아래/위에 새 내용을 반영합니다 (본 문서에서 이미 반복 사용 중인 패턴을 표준으로 확립).
- **레코드 단위 변경** (예: `defects.json`의 개별 결함 상태/담당자 변경): 레코드를 덮어쓰지 않고, 스키마에 있는 `history` 배열에 변경 전 상태를 이력으로 추가합니다 (20-2항 스키마 그대로 활용).
- **삭제도 동일하게 취급**: 파일이든 레코드든 완전히 사라지기 전에 위 방식 중 하나로 먼저 보존한 뒤 삭제를 진행합니다.
- **예외 — 자동화 테스트 코드/브릿지 소스 등 코드 파일**: 이 원칙의 대상이 아닙니다. Git 커밋 이력 자체가 코드의 변경 이력이므로, 이전 로직을 주석으로 남기지 않고 정상적으로 교체합니다 (죽은 코드/주석 처리된 옛 로직을 남기지 않는 일반적인 코드 품질 원칙을 그대로 따름).
- **⚠️ HTML 뷰어 생성 시 TC 데이터 이스케이프 필수**: TC 내용 자체에 `<script>`, `</script>` 같은 태그 형태 문자열이 들어있을 수 있습니다 (예: "쿼리 파라미터에 스크립트 주입 시 안전 처리 검증"류 보안 TC는 절차/테스트데이터 필드에 실제 `<script>alert(1)</script>` 문구를 담고 있음). 이를 이스케이프 없이 그대로 삽입하면 **뷰어 자체가 깨지거나(스크립트 블록 조기 종료) 의도치 않게 실행됩니다.** 뷰어 생성 시 반드시:
  - TC_DATA를 `<script>` 태그에 임베드할 때 `JSON.stringify(...).replace(/</g, '\\u003c')`로 `<`를 이스케이프
  - 각 TC 필드를 테이블 셀에 렌더링할 때 HTML 이스케이프 함수(`&`→`&amp;`, `<`→`&lt;`, `>`→`&gt;`, `"`→`&quot;`)를 거쳐 출력
- **⚠️ HTML 뷰어의 편집 내용 저장은 File System Access API로 실제 파일에 반영**: 실행결과/담당자/이슈내용/이슈링크(TC)와 상태/비고(결함)는 기본적으로 브라우저 메모리에만 있어 새로고침 시 사라집니다. 이를 실제 캐노니컬 파일에 반영할 수 있도록, "JSON 파일 연결/불러오기" 버튼으로 `window.showOpenFilePicker()`를 호출해 해당 JSON 파일의 핸들을 받고(`requestPermission({mode:'readwrite'})`로 쓰기 권한 확보), 이후 "저장" 버튼은 `handle.createWritable()`로 그 파일에 직접 씁니다. `window.showOpenFilePicker`가 없는 브라우저(Safari/Firefox 등)에서는 기존 `<input type="file">` + 다운로드 방식으로 자동 폴백합니다. TC 캐노니컬 파일과 `defects.json`은 별개 파일이므로 **연결/저장 버튼도 TC 목록用과 결함현황用을 각각 따로** 둡니다.

## 10-1. 캐노니컬 파일 전환 이전(마이그레이션) 절차

이 규칙(10항) 도입 이전에 만들어진 날짜 스냅샷 파일(`{프로젝트명}_TC_ALL_{날짜}.json` 등, 모듈 구분 없이 전체를 한 파일에 담은 형태)이 프로젝트에 남아있는 경우의 처리 절차입니다.

- **일괄 전환을 강제하지 않습니다.** 실제로 작업 요청이 들어온 모듈/소분류 범위만 그때그때 캐노니컬 파일로 이전합니다 (전체를 한 번에 마이그레이션하지 않음).
- **이전 방법**: 스냅샷 파일에서 해당 모듈코드에 속하는 항목(대분류/중분류 기준)을 추출하여 신규 `{프로젝트명}_TC_{모듈코드}.json`을 생성합니다. `meta.version`은 1부터 시작하고, `meta.changeHistory`에 `{ "version": 1, "date": "...", "summary": "레거시 파일 {원본파일명}에서 이전 (해당 모듈 범위만)" }`를 기록합니다.
- **원본 스냅샷 파일은 삭제하지 않습니다.** 이전된 항목은 원본 파일에 남겨두되, 원본 파일의 `meta`에 `migratedTo` 배열을 추가하여 어떤 항목(tcId 목록)이 어느 캐노니컬 파일로 이전되었는지 기록합니다:
  ```json
  "meta": {
    "project": "...", "generatedAt": "...", "totalCount": 165,
    "migratedTo": [
      { "module": "PD", "file": "{프로젝트명}_TC_PD.json", "tcIds": ["TC_PD_003", "..."], "migratedAt": "2026-08-18" }
    ]
  }
  ```
- 아직 이전되지 않은 모듈은 스냅샷 파일에 그대로 남아있으며, 해당 모듈 작업 요청이 들어올 때 같은 방식으로 이전합니다. 스냅샷 파일의 모든 항목이 이전 완료되면 그 시점에 사용자에게 원본 파일 보관/삭제 여부를 확인합니다.
- **⚠️ 신규 TC ID 채번 시 주의**: 부분 이전이므로 캐노니컬 파일에 옮겨진 항목 수만 보고 다음 번호를 정하면 안 됩니다. **반드시 원본 스냅샷 파일 전체에서 같은 모듈코드(`TC_{모듈코드}_`)의 최대 번호를 확인한 뒤, 그보다 큰 번호부터 채번**합니다 (스냅샷에 아직 이전 안 된 다른 소분류가 같은 모듈코드의 번호를 이미 쓰고 있을 수 있음).

## 11. 테스트 범위 균형

TC 세트 생성 시 아래 비율을 목표로 합니다:

| 구분 | 목표 비율 |
|------|---------| 
| 정상 (Happy Path) | 40% |
| 예외 (Sad Path / 오류 케이스) | 35% |
| 유효성 (경계값/필수·선택 입력값 검증) | 25% |

**"유효성" 범위**: 최소/최대값 등 경계값 검증뿐 아니라, **입력 항목의 필수(Required)/선택(Optional) 여부에 따른 유효성 검사**도 포함합니다.
- 필수 항목 미입력 시 차단 및 안내 문구 노출 여부
- 선택 항목 미입력 상태로도 다음 단계 진행 가능한지
- 형식 제한(길이, 특수문자, 자릿수 등) 위반 시 처리

## 11-1. 재사용 가능한 TC 패턴 라이브러리 ★

비슷한 유형의 검증(예: "필수 입력 검증", "최대 글자수 제한", "이메일 형식 검증")이 여러 화면·필드에 반복될 때, **매번 절차/기대결과 문장을 새로 쓰지 않고 공통 패턴을 재사용**합니다.

- **패턴 파일**: `{프로젝트명}\TC\patterns.md` (프로젝트별로 독립 — 다른 프로젝트의 패턴을 가져오지 않음, 16항 격리 원칙과 동일)
- **패턴 항목 구성**: 패턴명, 적용 대상 유형, 절차 템플릿(`{필드명}`/`{값}` 등 placeholder 포함), 기대결과 템플릿, 이 패턴을 사용 중인 TC ID 목록
  ```markdown
  ### 패턴: 필수입력검증
  **적용 대상**: 필수(Required) 입력 필드
  **절차 템플릿**:
  1) {필드명} 입력란을 비운 채로 다음 단계 버튼 클릭
  **기대결과 템플릿**:
  1) {필드명} 입력란 하단에 "{필드명}을(를) 입력해주세요" 문구 노출, 다음 단계로 진행되지 않음
  **사용 중인 TC**: TC_MBR_003(이메일), TC_MBR_004(비밀번호), TC_ORD_011(배송지)
  ```
- **적용 규칙**:
  1. TC를 작성하기 전, 지금 작성하려는 검증이 `patterns.md`의 기존 패턴과 일치하는지 먼저 확인합니다.
  2. 일치하면 패턴 템플릿에 실제 값(필드명, 문구 등)만 채워 넣어 TC의 절차/기대결과를 작성하고, 기준문서 컬럼 끝에 `· 패턴: {패턴명}`을 덧붙입니다.
  3. 같은 유형의 검증이 **이번 요청에서 3회 이상** 반복될 것으로 예상되면, 개별 TC를 쓰기 전에 `patterns.md`에 패턴을 먼저 정의합니다.
  4. 패턴의 절차/기대결과 자체를 수정해야 하는 경우(문구 변경 등) `patterns.md`를 갱신하고, 그 패턴을 사용 중인 TC 목록을 참고해 관련 TC들도 함께 갱신 대상으로 검토합니다.
  5. 패턴 재사용은 **작성 효율과 일관성**을 위한 것이지, 실제로 다른 근거(정책서/화면)를 가진 케이스까지 억지로 같은 패턴에 끼워 맞추지 않습니다 (7항 근거 원칙 우선).

### 5-1. 테스트 수행 결과 이력 관리

- Phase 5 테스트 수행이 끝나 캐노니컬 TC 파일(`{프로젝트명}_TC_{모듈}.json`)의 `result`/`issueSummary` 등 실행결과 필드를 갱신한 직후, 그 시점의 스냅샷을 별도로 보관합니다.
- 저장 위치/명명: `{프로젝트명}\TC\results\{프로젝트명}_TC_{모듈}_Result_{YYYYMMDD}.json` 및 동일 이름의 `.html`(HTML 뷰어 생성 스크립트로 같은 스냅샷을 렌더링).
  - 예) `데모사이트\TC\results\데모사이트_TC_PD_Result_20260819.json` / `.html`
- 같은 날짜에 여러 번 실행하면 그날의 스냅샷 파일을 덮어씁니다(하루 단위 이력이며, 하루 내 여러 회차까지 보존하지 않음). 날짜가 바뀌면 새 파일로 누적되어 실행 이력이 이어집니다.
- 캐노니컬 TC 파일(`meta.changeHistory`로 버전 관리, 10항)과는 별개의 이력 축입니다 — TC "정의" 변경 이력은 `TC\legacy\`, TC "실행결과" 이력은 `TC\results\`로 구분해 보관합니다.
- `results\` 스냅샷은 참고용 기록이므로 캐노니컬 파일처럼 `meta.version`을 올리거나 덮어쓰기 전 별도 아카이브를 요구하지 않습니다.
- 스냅샷 저장 후 `{프로젝트명}\TC\results\index.html`(전체 스냅샷 목록)도 함께 갱신합니다. GitHub Pages는 디렉터리 목록을 자동 제공하지 않으므로, 이 인덱스 페이지가 없으면 스냅샷 파일명을 몰라 접근할 수 없습니다.
  <!-- [수정 전 2026-08-24] 인덱스 표 컬럼을 "실행일/모듈/Pass·Fail 건수/링크"로만 명시하던 버전.
  Pass/Fail만 노출하면 대부분이 N/T인 모듈(예: 결함으로 막힌 모듈)이 "Pass+Fail=0"으로 보여 아무것도

  - **표 컬럼**: 실행일 / 모듈 / 전체 / 수행 / Pass / Fail / Blocked / N/A / N/T / 미실행 / **수행율**(수행÷전체) / **Pass율**(Pass÷수행) / **실패율**(Fail÷수행) / 보기(해당 스냅샷 링크) — "실패율"은 모듈별 뷰어 통계표의 "Fail율"과 같은 지표를 가리키는 동의어입니다(표기만 다름, 계산식 동일).
  - **전체 합계 카드**: 표 위에 "모듈별 최신 스냅샷 기준" 전체 합계(위 지표 전부 포함)를 별도로 보여줍니다. 과거 스냅샷을 모두 더하면 같은 모듈이 여러 번 중복 집계되므로, 반드시 **모듈별로 가장 최근 날짜의 스냅샷 1개씩만** 골라 합산합니다.
  - **전체 TC 뷰어 링크**: 헤더에 통합(Full) 뷰어(`{프로젝트명}_TC_전체.html`) 링크 버튼을 둡니다. 하단 안내문 등 다른 곳에서 특정 모듈 파일(예: PD)을 예시로 하드코딩해 링크하지 않습니다 — 모듈 예시 하드코딩은 실제로 다른 모듈 페이지를 열었을 때도 항상 그 모듈만 안내하는 오류로 이어진 사례가 있습니다(2026-08-24 발견).

## 17. 프로젝트 온보딩 (신규 프로젝트 추가)

1. `tc-automation\_template\`을 `tc-automation\{프로젝트명}\`으로 복사합니다 (Policy/SB/Requirements/Analysis/TC 빈 폴더 포함). **다른 기존 프로젝트 폴더를 복사하거나 참고하지 않습니다** — 항상 `_template\`에서만 시작합니다.
2. 고객/기획 측에서 받은 기준문서를 해당 서브폴더에 넣습니다 (정책서→Policy, 화면설계서→SB, 요구사항→Requirements). **`Analysis\`는 고객 제공 문서를 넣는 곳이 아닙니다** — Phase 1~3에서 어시스턴트가 직접 관찰·정리한 산출물(`{프로젝트명}_PRD.html`)만 여기 저장합니다.
3. 기존에 운영 중이던 레거시 TC가 있다면 `TC\legacy\`에 넣습니다.
4. 이후 TC 생성 요청 시 스킬은 자동으로 **이 프로젝트 자신의** `{프로젝트명}\Policy`, `\SB`, `\Requirements`, `\TC\legacy`만을 근거 자료로 스캔합니다 (다른 프로젝트 폴더는 스캔 대상이 아님). `\Analysis\`는 근거 자료가 아니라 이미 정리된 산출물이므로 스캔 대상에서 제외합니다.

## 18. Git 버전관리

- `tc-automation\`은 하나의 Git 저장소입니다 (`github.com/13ongdal-create/tc-automation`). 모든 프로젝트가 이 저장소 하위에서 함께 버전관리됩니다. **2026-08-24부터 `agents-config\`(이 파일 자신 포함)와 `slack-bridge\`도 git subtree로 이 저장소에 병합되어 같은 곳에서 커밋/push됩니다** — 더 이상 별도 저장소가 아닙니다(각자의 GitHub 저장소는 아카이브로만 남아있고 더 이상 push하지 않음).
- **커밋 대상**: `{프로젝트명}\TC\` 산출물(HTML/JSON), 기준문서(Policy/SB/Requirements), `{프로젝트명}\Analysis\` 산출물(PRD 등), `_reference`, `_template`, `agents-config\`(규칙/스킬 수정 시), `slack-bridge\`(브릿지 코드 수정 시), `dashboard\`(대시보드 코드 수정 시).
- **커밋 시점**:
  1. TC 생성 배치가 최종 승인되거나(Phase 4), 테스트 수행 결과가 보고되면(Phase 8) **그 즉시 자동으로 커밋**합니다 — 커밋 자체를 위해 별도로 "커밋해줘" 요청을 받을 필요는 없습니다.
  2. 여러 배치를 이어서 진행 중이면 배치 단위로 커밋합니다 (전체 완료까지 기다리지 않음).
- **⚠️ Push 시점 — 커밋과 분리, 매번 확인 필수**: 커밋까지는 자동으로 진행하되, **`git push`는 커밋 직후 바로 실행하지 않고 반드시 사용자에게 짧게 확인을 받은 뒤에만 실행**합니다 (예: "방금 커밋했습니다 — 원격(origin)에 push할까요?"). 같은 대화 안에서 이후 배치를 추가로 커밋하더라도 push는 매번 다시 확인합니다. 이 확인 없이 push를 자동 실행하지 않습니다.
- **커밋 메시지 규칙**: `{프로젝트명}: {작업 요약}` (예: `ABC마트: 상품상세 TC 32건 생성`, `ABC마트: 장바구니 TC P1 우선순위 수정`)

## 19. URL 기반 코드형 TC + 자동화 테스트 (Playwright)

정책서 등 기준문서 대신 **실제 서비스 URL**을 근거로 TC를 작성하고, 그 TC를 실행 가능한 자동화 테스트 코드로도 만들어 직접 돌려본 뒤 결과를 리포트하는 워크플로우입니다. 13항의 Phase 1~8과 결합되며, 아래 순서를 따릅니다.

1. **관찰(Inspect, Phase 1)**: 사용자가 제공한 URL로 Playwright 헤드리스 브라우저(Chromium, 이미 설치됨)를 직접 띄워 접속하고, 화면 구조(폼 필드, `required` 여부, 버튼, 텍스트, 상태)를 스크립트로 덤프해 `tc-automation\_scratch\{프로젝트명}\` 아래에 저장합니다 (9항과 동일한 스크래치 컨벤션, Git 비대상). 이 관찰 결과가 TC의 근거(7항)가 됩니다.
   - **⚠️ 속도를 위해 여러 검증 시나리오(예: 비밀번호 불일치/잘못된 형식/특수문자/미래 날짜 등 다수의 유효성 케이스)를 관찰할 때는, 시나리오마다 별도 스크립트로 브라우저를 새로 띄우지 않고 하나의 스크립트 안에서 브라우저 인스턴스 하나를 재사용해 순차 처리합니다.** 매번 `chromium.launch()`를 반복하면 실행마다 브라우저 기동 오버헤드(1~3초)가 누적되어 전체 소요 시간이 크게 늘어납니다.
   - 페이지 이동 대기는 꼭 필요한 경우가 아니면 `waitUntil:'networkidle'`보다 `waitUntil:'load'` 또는 `'domcontentloaded'`를 우선 사용합니다 (networkidle은 백그라운드 폴링이 있는 페이지에서 불필요하게 오래 대기할 수 있음).

2. **TC 문서 생성(Phase 3~4)**: 관찰된 요소를 근거로 기존 컬럼 스키마(SKILL.md 3항)에 맞춰 TC를 작성합니다. **기준문서 컬럼은 정책서/화면설계서 등 실제 문서가 존재하는 경우에만 그 문서명을 기재하고, 그 외(Playwright 관측만으로 작성한 경우)에는 `-`로 둡니다.** Playwright 관측 근거(URL/날짜)는 `tc-automation\_scratch\{프로젝트명}\`의 관찰 결과 파일로 이미 추적되므로 TC 행에 중복 기재하지 않습니다.
3. **자동화 테스트 코드 생성(Phase 4)**: 각 TC의 수행절차/기대결과를 Playwright 테스트로 변환해 `{프로젝트명}\TC\automation\tests\{모듈}.spec.js`에 저장합니다 (1 TC ≈ 1 `test(...)` 블록 원칙). **테스트 제목에 TC ID와 기능명(소분류)을 모두 포함**합니다: `test('[TC_CRT_012][쿠폰적용] 쿠폰 코드 입력 시 즉시 할인 적용 검증', ...)` — 이 형식이어야 특정 TC 하나 또는 특정 기능만 골라 재실행(`--grep`)할 수 있습니다 (19-1항). **반드시 `@playwright/test`가 아니라 `tc-automation\_shared\testFixtures.js`에서 `test`/`expect`를 가져옵니다** (경로는 항상 고정: `require('../../../../_shared/testFixtures')`). 이 공통 fixture가 모든 테스트에 브라우저 콘솔 에러(JS 예외)·실패한 API 요청(4xx/5xx) 자동 감지 + 실패 시 스크린샷 캡처를 적용해줍니다 — 어서션이 통과해도 콘솔/네트워크 에러가 있으면 해당 TC는 자동으로 실패 처리됩니다. **이 시점에는 코드만 생성하고 실행하지 않습니다** — Phase 4 산출물(TC 문서 + 테스트 코드)에 대한 승인까지만 받습니다.

- **⚠️ 관찰(Phase 1) 범위도 함께 좁히기**: 기능 단위 요청일 때는 Playwright 관찰도 **그 기능과 직접 관련된 화면/플로우로만 한정**합니다. 같은 상위 모듈에 속한 다른 기능(예: "회원" 모듈 요청 시 회원가입만 요청받았는데 로그인/마이페이지까지 함께 관찰)까지 넓혀서 관찰하지 않습니다 — 범위가 넓어질수록 관찰 시나리오 수가 늘어 실행 시간이 길어지고, 요청받지 않은 범위까지 TC가 생성되는 결과로 이어집니다.

- 결과 보고 시 "{모듈} 전체" 대신 "{모듈} > {기능명}" 또는 "TC_ID 1건"처럼 **실제 실행 범위를 명시**합니다.

## 20. 결함(Defect) 관리

자동화 테스트(19항)가 실패를 발견하면, 그 실패를 응답 텍스트로 한 번 보고하고 끝내지 않고 **`{프로젝트명}\TC\defects.json`에 결함 레코드로 영속화**합니다. Jira 등 외부 이슈트래커 없이 이 저장소 안에서 자체적으로 관리합니다.

### 20-1. 파일/폴더 컨벤션

- **레코드 파일**: `{프로젝트명}\TC\defects.json` (배열, Git 관리 대상)
- **스크린샷**: `{프로젝트명}\TC\defects\{결함ID}.png` — 실패 시점의 스크린샷을 `_scratch`/`test-results`(Git 비대상, 휘발성)에서 이 경로로 **복사**해 영구 보관합니다 (원본 경로만 참조하면 리포트 삭제 시 증거가 사라지므로 반드시 복사).

  - **자동화(Phase 5) 경로**: `_shared/testFixtures.js`가 실패 시 이미 `testInfo.attach('console-network-errors', {...})`로 같은 형식의 JSON을 첨부해두므로, 결함 레코드 생성 시 스크린샷과 함께 이 첨부파일도 위 경로로 복사합니다.
  - **수동 재현/Phase 1 관찰 경로**: 스크린샷을 찍기 전에 `page.on('console', ...)`/`page.on('pageerror', ...)`/`page.on('response', ...)` 리스너를 먼저 등록해 같은 형식(`consoleErrors`/`failedRequests`)으로 수집한 뒤, 스크린샷과 같은 타이밍에 저장합니다 — 스크린샷만 찍고 콘솔로그 캡처를 생략하지 않습니다.
- **결함 ID 형식**: `DEF_{프로젝트명}_{3자리 순번}` (예: `DEF_ABC마트_001`)

### 20-7. 기존 결함으로 재검증이 막힌 TC — N/T 처리 (2026-08-21 확정)

같은(또는 상위) 결함이 이미 `신규`/`처리중` 등 미해결 상태로 등록되어 있어서, 그 결함 때문에 특정 TC가 정상적으로 Pass/Fail을 판정할 수 없는 경우(예: 로그인 플로우 자체의 알려진 리소스 404가 그 플로우를 거치는 모든 TC를 자동으로 실패 처리시키는 경우) 처리 방법입니다.

- **실행결과**: `Fail`이 아니라 **`N/T`**로 기록합니다 — 이 TC 자체의 기능이 깨졌다는 뜻이 아니라, 이미 알려진 다른 결함 때문에 깨끗한 판정이 불가능하다는 뜻입니다.
- **비고(remark)**: `"해당 결함에 따른 테스트 불가 (관련 결함: {결함ID})"` 형식으로 기재합니다. 관련 결함이 여러 개면 쉼표로 나열합니다.
- **관련 결함 판단 기준**: `defects.json`의 `tcId` 필드와 정확히 일치하는 TC뿐 아니라, **같은 근본 원인(예: 로그인 플로우 프리페치 404, 배너 href 프로토콜 누락)으로 인해 실패하는 다른 TC들도 모두 포함**합니다 — 결함 하나가 여러 TC에 파급되는 경우가 많으므로 tcId 1:1 매칭에 국한하지 않습니다.
- **결함 자체를 재현/확인하는 목적의 TC**(예: "OOO 접근 시 404 에러 검증"처럼 그 결함 발생을 검증 대상으로 삼는 TC)는 N/T가 아니라 **의도된 대로 Fail 유지**합니다 — 그 결함이 실제로 재현되는지 확인하는 것이 이 TC의 목적이므로, 결함이 해결되지 않은 한 계속 Fail로 남아 있는 것이 정상입니다.
- 해당 결함이 `완료` 처리되면, 관련된 N/T TC들도 함께 재실행하여 정상 Pass/Fail로 갱신합니다(기계적으로 자동 전환하지 않고 재실행 후 실제 결과로 반영).

### 20-8. 라이브 환경 자동화의 안정성 (2026-08-21 확정)

- **특정 상품ID·정확한 개수 등 라이브 데이터를 하드코딩하지 않습니다**: 상품 상세 페이지, 카테고리 상품 개수, 가격 슬라이더 최대값처럼 운영 중 계속 바뀌는 값을 특정 숫자/특정 상품ID로 고정해서 검증하면, 그 데이터가 바뀌는(상품 판매종료, 신규 입고 등) 순간 자동화가 깨집니다. 대신:
  - 상품 상세 검증은 카테고리 목록에서 **첫 번째로 노출되는 상품**에 진입해 임의의 상품이 정상적으로 노출되는지(상품명·가격·코드 형식 등 구조적 요소)를 검증합니다.

  - 페이지네이션처럼 데이터량에 따라 존재 여부가 갈리는 요소는 클릭 전에 존재 여부를 먼저 확인합니다.
  - 특정 값 자체가 TC의 핵심 검증 대상인 경우(예: 존재하지 않는 상품ID 접근 시 처리 검증)는 예외입니다 — 그 값이 실제로 존재하지 않음을 이용하는 것이 테스트 의도이므로 하드코딩이 아닙니다.
